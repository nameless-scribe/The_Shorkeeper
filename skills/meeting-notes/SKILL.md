【技能：会议纪要】

固定流程是"转写 → 读逐字稿 → 出纪要 → 和用户确认 → 确认后才写入"。转写按时长计费且要用户确认，纪要便宜且经常要改，所以两者永远是两步，不要合并。

一、定位录音与逐字稿
1. 用户没给文件名时，先 `list_dir` 找工作区里的音频（m4a / mp3 / wav 等）；有多个就列出来让用户选，不要猜。
2. 转写前先看同目录有没有 `<音频名>.transcript.md`。有就直接 `read_file` 读它，**不要再调 `transcribe_audio`**——重复调用会让用户再确认一次并可能重复计费。
3. 没有逐字稿才调 `transcribe_audio`。它只返回路径、时长、句数、说话人数和开头片段，正文要用 `read_file` 读。长会议的逐字稿可能上万字，分段读，不要一次读完再全文复述。
4. 用户只要逐字稿、没提纪要时，转写完给出路径和摘要就停下，不要主动写纪要。

二、写纪要
逐字稿每行形如 `**[mm:ss] 说话人 N**　内容`。纪要按下面的结构写在对话里：

- 基本信息：录音文件、时长、说话人数、逐字稿路径。
- 议题与结论：每条议题一句结论，末尾标注依据的时间戳，如 `[03:12]`。
- 待办：表格，列为 事项 / 负责人 / 截止 / 依据。**依据必须是逐字稿的时间戳加原话摘录**，让人能回去核对"他到底怎么说的"。
- 未决事项：会上提到但没有结论的，单独列出。

规则：
- 只写逐字稿里有的内容，不补充会上没说的信息；识别有歧义的地方用「？」标出并说明。
- 相对日期（"下周三"、"这周内"、"下个月十五号"）要换算成具体日期。基准是录音日期：文件名或用户说了就用那个，否则问用户，不要按今天猜。
- 说话人只有"说话人 1、2"这样的标签。纪要里先沿用标签，在确认环节问用户哪位是本人、其他人叫什么；用户不说就保留标签。

三、确认
纪要给出后，明确问用户三件事，等回答后再动手：
1. 纪要内容是否有误、要不要改。
2. 说话人对应关系：哪位是用户本人。这决定了每条待办归谁。
3. 哪些待办要记进系统。逐条列出建议的处理方式让用户点头。

四、确认后写入
- 用户自己负责的事项 → `create_user_task`：`title` 用事项本身，`due_at` 用换算后的日期，`module` 用会议名或项目名，`notes` 写"来源：<逐字稿路径> [mm:ss] 原话"。
- 用户在会上答应了在场某人的事 → `manage_commitments` 的 `record`，`promised_to` 填对方，`title` 与 `due_at` 同上。它会自动创建关联待办，**不要再用 `create_user_task` 重复建**。
- 别人负责的事项 → **不建待办、不建承诺**，只留在纪要里。用户明确说要跟进时，才以用户自己的名义建一条"跟进：某人的某事"待办；`promised_to` 只记录事实，从不代别人做承诺。
- 写入前可用 `list_user_tasks` 看是否已有同样的待办，避免重复。
- 用户确认后再用 `gen_markdown` 把纪要写到逐字稿旁边：`<音频名>.minutes.md`。
- 用户拒绝、犹豫或没有回答：什么都不写，包括纪要文件。纪要留在对话里即可，用户随时可以要求改格式或再总结一次。

五、写完之后
一句话汇报写入了几条待办、几条承诺、纪要文件路径。不要复述整份纪要。
