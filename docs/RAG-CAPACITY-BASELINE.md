# RAG 容量基线

> 版本：0.1.0  
> 日期：2026-09-13  
> 命令：`pnpm rag:capacity`  
> 环境：Windows x64、Node v22.20.0、better-sqlite3、256 维合成向量

## 1. 用途

该基线用于观察原生 SQLite、FTS 和当前内存向量扫描在知识库增长时的方向性变化。它不调用外部 Embedding 服务，不评价回答质量，也不代表硬性产品上限。

每次运行都会在系统临时目录创建独立数据库，写入合成文档和 chunks，完成 WAL checkpoint 后记录数据库大小，并自动删除临时目录。

## 2. 2026-09-13 基线结果

以下数值为同一环境连续三次独立运行的中位数：

- small：50 文档、1,000 chunks；建库写入 88.5 ms，向量加载 2.7 ms，扫描 3.3 ms，FTS 1.1 ms，数据库 2.09 MiB，RSS 增量 12.75 MiB。
- medium：250 文档、5,000 chunks；建库写入 446.5 ms，向量加载 12.0 ms，扫描 7.8 ms，FTS 4.1 ms，数据库 9.35 MiB，RSS 增量 22.96 MiB。
- reference：500 文档、10,000 chunks；建库写入 943.3 ms，向量加载 26.2 ms，扫描 9.1 ms，FTS 7.6 ms，数据库 18.46 MiB，RSS 增量 48.45 MiB。

每档向量和 FTS 均返回 20 个候选。初始化耗时约 35–40 ms。

## 3. 当前结论

- 10,000 chunks 参考档在当前机器上仍处于可接受范围，没有触发更换 SQLite 或向量存储技术的证据。
- 当前检索会把活动 chunks 的文本和向量载入进程缓存；参考档三次运行的 RSS 增量中位数约 48.45 MiB，因此更大规模下应重点观察常驻内存，而不是只看单次查询耗时。
- 全量向量扫描目前仍是线性复杂度。只有真实知识库明显超过参考档，或 H3 长稳显示内存/延迟门槛失守时，才评估 ANN/独立向量索引。
- 数值会受 CPU、磁盘缓存、GC 和后台负载影响；后续比较应在同一环境重复运行并关注趋势。

## 4. 后续门槛

- [x] H3 连续运行三次并记录中位数；后续版本升级继续保留三次运行规则。
- 增加真实分块长度的样本，避免合成短文本低估文本缓存占用。
- 若 50,000 chunks 时 RSS 或首次检索不可接受，再建立分段加载、量化或 ANN PoC；在此之前不更换技术栈。
