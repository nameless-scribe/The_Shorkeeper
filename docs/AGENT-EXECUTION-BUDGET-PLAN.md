# Agent 执行预算、完整性与续跑方案

日期：2026-09-18。状态：A、B 基础防护及 C 的明确授权检查点续跑已实现；自动续段、B 语义进展/重试、正式 paused 状态和 D 尚未完成。首批历史记录见第 10 节，当前续跑范围见第 11 节。

起因：用户在真实数据库查询中遇到“已达到最大工具轮次 (10)”。本方案根据当前代码检查提出；除用户报告的轮次中断外，下面的触发场景属于代码路径确认或风险推导，不冒充已发生的实机故障。

## 1. 结论与边界

采用“分段预算 + 可核验进展 + 明确收尾 + 有证据的续跑”。保持资源有界、权限确认、只读数据库与产物证据要求。轮数只是防护维度之一，不能作为任务复杂度和完成状态的唯一判断。

本方案最初由只读检查形成，以下第 2 节记录改动前基线。当前实施状态以第 10、11 节为准；第 3 至 9 节仍包含后续设计，不代表全部已实现。检查范围包括 Agent 主循环、上下文、提问/权限等待、查询与导出、视觉、文件转换及模型协议的结束处理；不是对全仓所有限值的穷尽审计。自动化不连接用户数据库、不调用真实模型。

## 2. 当前事实与相似问题

### 2.1 任务达到 10 次模型请求后直接失败

- `src/agent/loop.ts`：`maxRounds = 10`，每次模型请求之前递增；一批工具执行结束后才回到循环检查。
- 第 10 次模型回复若没有工具调用，可以正常结束；若有工具调用，即使全部成功，循环结束仍产生 `run_error`，没有独立总结机会。
- 单次模型回复另有 20 个工具调用的洪泛限制，不能与任务总轮数混为一谈。
- `src/agent/orchestrator.ts` 收到 `run_error` 立即返回，跳过正常的 assistant 消息持久化；成功步骤和产物仍可有运行记录。
- `src/agent/loop.ts` 最后清理内存计划；`run-recovery.ts` / `task-runs.ts` 现有恢复说明仅查询 `interrupted`，不会自动接管这种 `error`。

结果：用户看到失败，但之前的查询、文件写入可能已成功；发送“继续”创建新 run，不能视为精确恢复旧任务。

### 2.2 提问等待存在 10 分钟与 2 分钟的嵌套冲突

- `electron/ipc/ask.ts` 给提问 10 分钟；`loop.ts` 却仍用普通工具 120 秒计时器包住 `ask_user.execute`，并传递其取消信号。
- 因此在 Agent 中等待回答超过 2 分钟，外层就能先中止问题。
- 权限确认不同：`authorizeToolCall` 位于正式工具执行计时器之外，5 分钟权限等待不受这个 2 分钟外层限制。应推广这个已有模式。
- 提问未回答时，目前工具失败回到模型，依赖提示词让模型停下；主循环没有统一的“缺少关键回答，暂停依赖步骤”闸门。

### 2.3 单次操作超时没有区分进展与等待性质

- 模型与普通工具默认都采用 120 秒总时长；模型在持续输出时也不会刷新这个计时器。
- MCP 调用另有 60 秒、MySQL 查询默认 30 秒、视觉请求 30 秒。外层可比领域流程更短，领域流程也可能累计多个子操作。
- `awaitWithAbort` 只保证停止等待，不保证不响应 signal 的工作真的停止。`convert-markdown.ts` 的 DOCX/DOC 转换路径及之后的原子提交没有完整取消检查，`writeWorkspaceFileAtomically` 目前也不接收 signal。

风险：长文档处理可能已被界面报为超时，底层随后仍落盘。这是代码推导的潜在路径，需要延迟转换器回归测试确认，不应把超时等同于“未执行”。

### 2.4 上下文既会失去信息，又缺少循环内的完整预算

- `loop.ts` 的全部工具结果共享 8000 token 预算：新结果保留，旧结果截断或替换成省略提示；单批结果还会按调用数量平分预算。
- `formatToolResultForModel` 只送 output/error，完整的结果 metadata 不自动进入模型上下文。
- `orchestrator.ts` 在 run 开始时按默认 24000 输入 token 配置裁剪历史；循环中仅重新压缩工具文本，没有对新增 assistant 内容、tool_calls 参数和完整协议消息重新执行总预算控制。

风险：复杂任务里早先确认的口径、表结构、错误原因可能被挤出；简单增加轮数还会增加总上下文溢出的机会。8000 与 24000 分别是结果正文预算与初始输入预算，都不是任务总费用预算。

### 2.5 P7 追问与重试规则过于依赖模型

- `skills/data-query/SKILL.md` 要求“最多问 2 个”，随后缺信息就按默认值；这与关键业务口径不明确时不能猜测的要求存在张力。并非每次都会算错，但复杂问题可能仍有第三个必答信息。
- `run-sql-query.ts` 从模型参数读取 `attempt`，未给默认 1；失败到第 3 次时只在返回文案中要求停止。
- 没有主进程维护的实际重试账本，也没有在执行前按实际次数拒绝；模型持续传 1 或再次传 3 都能再次进入查询执行。

结果：合理任务可能被追问数量卡住，而真正重复失败又只能靠全局 10 轮兜底。

### 2.6 数据量限值与“结果完整”没有统一契约

- MySQL 连接器默认最大返回 500 行、硬上限 5000；实际查询工具还按方案 limit 与 max_rows 限制，常常更少。聊天预览前 20 行是另外一层。
- `run-sql-query.ts` 写入 CSV 的是本次取得的行；输出虽可能提示截断，仍包含“完整结果在……”文案。导出工具只转换该 CSV，不会自动补查剩余数据。
- `query-runner.ts` 以 EXPLAIN 各表 rows 相乘，超过 200 万拒绝执行。这是保守估算，不能等同于实际扫描量或确切耗时。
- 自检请求失败时记录 `ok: null`，目前不一定阻止结果成功，也不一定进入用户可见 output。扩大查询规模前必须明确“已验证 / 未验证 / 部分数据”。

### 2.7 视觉与模型输出存在另外的截断边界

- 视觉单次最多 6 张、单 run 最多 10 次请求/30 张图片；在同一 run 内再分批不会重置累计预算。缓存命中不扣视觉调用预算，但仍消耗 Agent 往返。
- `bailian-vl.ts` 的输出上限为普通回答 1024 token、读文字 4096 token；返回解析未检查 `finish_reason`，可能把截断文字当成成功结果保存为 sidecar，并在后续命中缓存。
- 主对话 OpenAI/Anthropic 适配器也未把供应商的长度截断原因完整传播到统一 `ModelEvent`；Anthropic 请求固定 `max_tokens: 8192`。输出长度耗尽不能与自然结束等同。

### 2.8 有些限制已有正确处理方式，应保留并复用

- `read_file` 超过 100000 字符时提示按行区间读取。
- Excel 已有 `start_row`、`returned_rows`、`has_more`，能继续读取后续页。
- 图表最多 50 类、文档正文 200000 字符、单次批量修改数量限制，保护可读性与资源；需要分段/汇总，不应一律放宽。
- 路径授权、只读 SQL、密钥隔离、破坏性操作确认、文件大小与协议消息上限继续硬性执行。
- 安静时段与通知预算代表用户的打扰偏好，不随任务轮数自适应调整。

## 3. 统一定义预算的归属

沿用现有 session → TaskRun → step/approval/artifact，不新增第二套任务系统。

- 会话：聊天历史容器，不共享一个不断减少的执行轮数余额。
- run：一次执行段。预算到限时以明确的暂停原因收口。
- 续跑链：后续 run 引用同一任务的根 run 和上一个 checkpoint；累计轮数、token、费用与领域配额持续记录，避免通过新 run 悄悄清零。
- 模型轮次：一次模型请求；失败请求也记资源消耗。普通文字最终答复也占一次请求，应在预算中预留。
- 工具调用：按真实调度与实际执行分别记数，记录拒绝、缓存命中、重放合并，不能把缓存命中当作新的业务进展。

## 4. 分段预算与自动续段

### 4.1 建议试运行参数（待 10 个真实问题校准）

首轮采用 20 次工作模型请求的软预算，每次可自动追加 10 次；本次授权额度最多 60 次工作请求、120 次工具调度、15 分钟有效执行时间、600000 累计输入加输出 token，任何一项先到都停止调度新业务步骤。token 候选值需与单轮输入预算一起校准，避免 24000 token 的上下文尚未跑到第一段就被另一个过小的累计阈值截停。

这些是候选值，不是模型能力或供应商限制；最终由真实任务的轮数、耗时和 token 分布校准。达到软预算不自动征求用户确认，符合进展条件时直接追加并给一条简短进度说明。

从总额度内提前保留一次只总结的模型请求及其完整输入预算和最多 2000 输出 token；若连收尾预算也不足，使用确定性模板列出已验证事实。费用仅在已配置可靠模型单价时作为附加限制，不能编造金额；usage 缺失时采用保守估算并标记，不能视为零消耗。

有效执行时间包括模型请求、工具执行、受控重试等待和收尾，不包括等待用户回答/审批；等待用户另有到期策略。挂起/休眠恢复时使用已有 power-lifecycle 协调，不能把整段等待误算成模型或工具卡死。

### 4.2 可核验进展

是否续段由主进程根据最近一段的证据判定，不能让模型自己报告“我有进展”来续费。

认可的证据包括：定位到新的必要表/字段或文件；用户补充了缺失口径；查询从失败变成有验证记录的成功；分页游标前进；新页完成识别；产物生成并通过存在/大小/哈希验证。

不单独认可：多说一段解释、仅更新计划状态、同参数重复读取同一版本、相同错误再次出现、凭空修改参数但没有新增有效证据。工具 success 也不等于整个用户任务完成。

首次落地采用确定性规则，不引入另一个模型充当“进度裁判”。记录规范化工具参数摘要、目标版本、结果状态、页码/游标/产物证据；敏感原值不进运行日志。

### 4.3 无进展与重试

同一子任务里，相同调用得到相同错误两次先要求改变策略，第三次阻止该重复调用。这个阈值为初始策略，应区别有明确进度和退避的轮询，不误伤正常分页或文件更新后的重新读取。

SQL 修复预算归属“当前确认的查询任务”，由宿主分配身份并计数；小改 SQL、改 attempt 或换工具调用 ID 不重置。用户改变业务问题才允许创建新查询任务。具体次数、错误类型和最终状态进入运行记录。

网络重试限于可重试错误且有次数和退避；权限拒绝、非法输入和结果不确定的副作用不能通用自动重试。无进展时先尝试有依据的替代路线；没有合理路线就说明阻碍并暂停。

### 4.4 硬限制

单批 20 个工具调用的洪泛保护保留。超批时整批不执行，返回有界、协议合法的失败说明，允许一次缩小批次的修正；不执行前 20 个后静默丢弃剩余调用。

权限、只读 SQL、授权目录和资源硬上限不由“任务复杂”绕过。达到一次授权的硬额度后需要用户明确续一段，界面展示已经花费和将增加的额度。用户继续授权与工具副作用审批仍是两件事。

## 5. 到限后的收尾与继续

### 5.1 收尾

达到预算阈值时不再启动新业务步骤。在正在执行的工具已结束且完成证据核验后，固化检查点，进入现有 finalizing 流程的受限分支。

模型收尾调用不注册业务工具，不能在总结阶段继续查库、写文件或保存记忆。输出只包括已确认完成、未完成、已有文件、停止原因、可继续的下一步。模型不可用时由宿主直接渲染这些事实，不能因“总结失败”隐藏已有产物。

用户文案示例：“已核对报工明细并生成 CSV；Excel 导出尚未执行。本次处理额度已用完，进度已保存，可以继续导出。”状态标为“已暂停，待继续”，不能标成全部成功，也不应笼统显示系统错误。

### 5.2 可靠的检查点

持久化最小必要信息：原始目标与确认口径、成功步骤引用、必要结果摘要与受管结果引用、已验证产物、分页位置、待完成步骤、预算累计、源版本/哈希以及结果未知的操作。

当前 step 账本没有完整工具参数和结果，内存计划也会被清掉；仅靠现有记录不能承诺恢复。因此需扩展现有 Repository 和有序 migration，增加暂停/续跑关联及有界检查点；不把任意模型上下文或密钥直接序列化进库。缓存/结果引用须有大小、保留期和删除联动策略。

记录失败时不能显示“进度已保存”或开放自动续跑；保留可验证的产物并报告保存失败。现有 recorder 的尽力记录可保留用于一般诊断，但不能作为恢复安全的唯一依据。

### 5.3 续跑规则

复用现有 agent IPC、会话运行锁与权限链。继续按钮携带明确的 run/checkpoint 标识，以事务认领防止双击或并发创建两次续跑；原 run 保持原终态，新 run 链接原记录。

开始前重新检查数据源、文件版本、产物哈希、权限策略和检查点有效性。源已变化则使相关结果失效，并说明需要重新核对。已经成功的非幂等步骤不自动重放；曾经批准过某动作也不等于批准了变更后的新动作。

重启后从检查点恢复事实，再由用户选择继续；不自动重放未知副作用。不支持可靠恢复的旧记录仍仅显示已有步骤与产物，不能伪造检查点。

## 6. 超时、取消和等待

- `ask_user` 移出普通工具执行计时，沿用权限等待的注入模式；10 分钟到期记录 awaiting-input 类暂停事实。关键回答缺失时宿主停止依赖动作，同批后续工具也受约束。
- 模型区分连接/首响应、无输出间隔、绝对总时长；持续输出可刷新空闲计时，但不能无限刷新总预算。推理增量是活动信号，不是业务进展。
- 工具沿用现有定义扩展运行策略字段，明确类别、超时、可取消性和允许的进度报告；不用另建执行器体系。文件转换、语音、SQL、MCP分别设置领域限制。
- 外层管理整个任务额度，内层管理单操作额度；子操作不能悄悄延长授权总额度。对话时间预算不直接替代数据库自己的超时。
- 超时先取消并等待有限的清理期；不可合作取消的 CPU/第三方转换应放入可终止的 worker/进程。原子提交前检查取消，提交已发生则按事实验证并记录，不能倒写成“未执行”。
- 清理仍不能判定结果时标记 outcome-unknown 类步骤，阻止对同一目标的重试/冲突写入，先核对副作用。释放会话锁不应解除目标冲突保护。

## 7. 上下文与大结果完整性

每次模型请求之前重新预算完整输入：系统指令、工具定义、用户目标、历史、assistant/tool_calls、工具结果，以及预留输出和协议开销。保守估算必须标记，不把它当成精确 tokenizer 计费值。

固定保留用户目标、已确认口径、权限约束、当前计划、未解决错误与证据引用。长结果使用摘要 + 有界结果引用 + 按需读取；复用现有文件/产物机制，内部短期结果不混入用户已交付产物列表。不能只用省略号替换唯一一份业务信息。

扩展统一结果契约，区分完成状态、数据覆盖范围、验证状态和继续读取方式。兼容已有 success 字段，逐步迁移调用方。完整性状态必须进入给模型的正文、聊天展示及导出来源页，不能只放在 metadata。

数据库的“只展示前 20 行”“返回前 N 行”“用户只要 Top N”“完整符合条件结果”必须分开。大查询优先在库内聚合、筛选；全量导出用有界流式/分页路径，不把所有行塞入模型。跨页保持稳定排序与必要的一致性保证，无法保证就明确说明。提高数据库成本阈值必须有明确源范围和用户授权。

视觉长文识别按页/区域分段，记录覆盖页码和页内完整性；检测供应商 finish_reason/stop_reason，截断结果标为 partial，不能写成完整缓存。主模型同样传播长度截断，工具参数不完整时禁止执行。后续续写属于预算内的受控操作。

## 8. 分阶段实施

### A：先修确定的终止和等待错误

让第 10 次工具成功后仍能安全收尾，记录专门的预算耗尽原因并输出已完成事实，修复 ask_user 的 2 分钟外层中止和未回答时的控制流。本阶段先使用现有终态及 terminalReason 兼容表示“本段已停止，目标未完成”，不宣称精确续跑已可用；正式 paused 状态、迁移与继续按钮在 C 接入，也不单独把轮数放大到 60。

### B：补齐任务预算与上下文控制

增加主进程预算策略和实际调用计数，按每次请求检查全部上下文，宿主维护 SQL 重试/无进展检测。为扩展额度准备数据依据，观测记录包括命中何种限制、当时是否有进展、耗时、token 和用户等待时间。

### C：检查点、续跑与界面

在现有 TaskRun、Repository、preload、trustedIpcMain、运行记录和工作流 UI 中接线。运行态、checkpoint、迁移与双适配器验证完成后才开放继续按钮；随后启用自动续段。语音保持短交互，定时任务沿用已有调度/主动提示，达到额度记录暂停并等用户处理，不创建新的无限重跑定时任务。

### D：领域限值与完整性

接入长文档取消、视觉分页/部分缓存、查询分页与导出完整性、自检未完成状态。优先数据库，其次提问和文档/视觉，不一次重写全部工具。已有按行/按页读取方式继续沿用。

每阶段可独立验证；修改状态/迁移/IPC时同步 DATABASE、DESIGN、使用说明及专项文档。UI 沿用 keeper-* 和共享组件，检查实际 Electron 的默认/替代主题、最小尺寸与 StrictMode。

## 9. 验收条件

自动化均使用临时数据与假模型，不接触用户应用库或业务库：

1. 重现原故障：第 10 次工具成功仍能展示已验证结果；第 11 次以后仍有进展的复杂任务能继续，达到真正硬预算则停止。
2. 一直重复失败的任务提前终止；持续更换调用 ID、attempt 或 SQL 小变体不能绕过宿主计数；正常分页/轮询不误判。
3. 第 3 分钟回答 ask_user 仍有效；10 分钟到期或用户取消后不执行依赖步骤；权限超时和问题超时各自明确。
4. 收尾时模型尝试调用工具也不会执行；收尾模型失败仍有确定性产物与剩余步骤说明。
5. 续跑双击、重启、源文件变化、检查点缺失、权限变化、保存失败都得到正确处理；非幂等动作不重放；结果未知动作必须先核对。
6. 长工具超时后不得悄悄提交文件；若已完成提交，运行记录不能显示为未执行并自动重试。
7. 多轮压缩后仍保留已确认业务口径；每轮完整输入和输出预留不超过配置预算。
8. 超过 5000 行数据、只要 Top N、导出截断 CSV、自检未执行等情况均准确说明覆盖/验证状态。
9. 超过视觉调用/图片预算可暂停后继续未完成页；输出 token 截断不缓存为完整成功。
10. 现有 S2/S3/P0/P6/P7/P8 相关测试、typecheck、build、Electron/StrictMode 和需要的双适配器迁移测试按开发契约执行。

实机使用用户已有 10 个问题，固定本地备份的数据时间范围与业务期望；每题记录实际轮数/工具数、失败原因、追问次数、耗时、token、是否暂停/重复执行和人工核对结果。先取得当前基线，再与改进后比较。通过率提升必须来自真实结果，不能仅依据“没有触发上限”。
