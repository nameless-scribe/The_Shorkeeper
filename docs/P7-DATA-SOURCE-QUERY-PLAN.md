# P7 · 数据源查询实施计划

> 计划验收入口：逐阶段补齐 `pnpm test:p7`，以及第 3 节的**评测集**通过率
>
> 阶段编号沿用 P 系列。P7 是已取消的 P2（外部连接器）的收窄版：只连 MySQL、只读、
> 把"我说想法 → 它组 SQL → 出 Excel 或图表"跑通，并且**越用越准**。依赖 P5 的产出工具与 P6 的追问机制。

当前状态（2026-09-17）：**P7.0–P7.5 主体代码已实现；P7.6 真实库验收未完成**。用户报告已在应用中配置本地备份库并点击刷新结构，连接结果、字典内容与查询结果仍待核对。首轮基线按用户决定使用现有 10 个真实问题（其中 4 个标 `mustAsk`），不再要求为凑数补到 20 个；`slots` 与 `aggregate` 的业务正确性须人工核对。实施记录见第 12 节。

**用户已明确的范围（2026-09-14）**：第一版只连 **MySQL**；SQL Server 与其它数据库搁置，等真实需求。
用户此前做过类似功能，**效果不好**——第 2 节先回答"这次为什么会不一样"。

## 1. 目标与边界

**要解决的**：用户用自己的业务语言提问，助理读懂库结构与业务口径、口径不明时先问、
生成只读 SQL、校验后执行、把结果变成 Excel 或图表，并把每一次确认过的问答沉淀下来，
让下一次同类问题更准。

**不解决的**：任何写库操作、跨库联查、通用 SQL 编辑器、MySQL 之外的数据库。见第 8 节。

**蓝图约束**："不开放高危系统权限"。外部数据库对本项目是高危面，因此**连接层就只读**，
不靠提示词约束模型不写。

---

## 2. 为什么"自然语言转 SQL"通常效果不好，这次怎么做

这类功能失败的原因高度集中。逐条列出，并写明本计划对应的机制。
**每一条机制都是本计划的验收项**，不是愿景。

| # | 失败原因 | 典型表现 | 本计划的机制 |
|---|---|---|---|
| 1 | **模型只看到表结构，看不到业务含义** | 列名叫 `f_amt1`、`status` 是 1/2/3；模型猜错表、猜错列 | **数据字典**（3.1）：表和列的说明、枚举值含义、哪张表是真源、哪些连接是合法的。自动抓一份骨架，**由用户和确认过的查询逐步补全** |
| 2 | **业务口径没有定义** | "销售额"每次算法都不一样 | **指标定义**（3.2）：命名指标带 SQL 片段与口径说明；未定义的指标必须先问（P6） |
| 3 | **直接从问题跳到 SQL** | 用户看到一段 SQL，看不懂对不对 | **两段式**（3.3）：先出一份人能读懂的**查询方案**（用哪些表、怎么连、按什么口径、什么粒度、什么时间基准），用户确认后再生成 SQL |
| 4 | **结果对不对没人知道** | SQL 跑出来一个数，用户无从核对 | **可核对的结果**（3.5）：每次执行返回行数、样例、方案摘要与 SQL；产物带来源；每个数字都能追到方案 |
| 5 | **连接放大** | 一对多 JOIN 后再 SUM，金额翻倍 | 字典记录外键基数；方案里必须声明**粒度**；校验器对"JOIN 后直接聚合且无 DISTINCT / 无子查询分组"给出警告并要求方案说明 |
| 6 | **时间口径混乱** | 时区、日期与日期时间、"上个月"按哪天算 | 字典里为每张事实表标注**时间基准列**；工具注入当前日期与连接时区；日期范围一律左闭右开；相对时间必须在方案里写成绝对区间 |
| 7 | **大库塞不进上下文** | 几百张表全给模型，它挑错 | **按需取表**（3.1）：先给表清单与一句话说明，模型再取具体表；字典可用现有 RAG 检索 |
| 8 | **SQL 错了就完** | 语法错、函数名错、字段名错 | **修复循环**（3.4）：先 `EXPLAIN`，报错回给模型改写，最多 3 轮；仍失败就如实告诉用户哪里不对 |
| 9 | **慢查询拖死** | 全表扫描、超时 | `EXPLAIN` 估算行数超阈值先问用户缩小范围；30 秒超时；可取消；行数上限 |
| 10 | **不会从纠正里学习** | 用户说"不对，要含退款"，下次照错 | **学习循环**（3.6）：确认过的问答存为命名查询并作为相似问题的示例注入；纠正写回字典与指标；口径进记忆候选 |
| 11 | **没有度量，不知道有没有变好** | 改了提示词，感觉好一点，说不清 | **评测集**（3.7）：首轮用 10 个真实问题，每次改动后重跑；自动指标与人工核对分开记录 |
| 12 | **用户被迫看 SQL 和术语** | 回复里大段 SQL、表名、字段名；开发者能看懂，别人不能 | **业务语言优先**（3.11）：SQL 与表名是执行细节，默认不出现在对话里；方案、追问、确认、结果、错误全部用业务语言；技术细节收在"详情"里给开发者 |

用户确认（2026-09-14）：**上一次这 12 条全都发生过**。其中第 12 条是产品层面的：
功能再准，用户看到的是 SQL 就不会用。因此本计划把"业务语言优先"列为与"只读"同级的硬约束，
第 3.11 节单独规定，停线条件里也有它。

## 3. 设计决定

### 3.1 数据字典（核心资产）

连接成功后自动生成**骨架**：表、列、类型、主键、外键、行数估计、每列前 3 个非空样例值（文本截断 40 字）。
骨架之上是**人工层**，每张表、每列可填：

- **业务名**（表：`orders` → "订单"；列：`paid_amount` → "实付金额"）。这是 3.11 的基础：对话里出现的永远是业务名，不是表名列名；
- 说明（一句话）；
- 枚举值含义（`status: 1=待付款 2=已付款 3=已退款`）；
- 是否真源（同一业务有多张表时指明该用哪张）；
- 时间基准列（事实表必填，见 2.6）；
- 合法连接（`orders.customer_id → customers.id`，基数 N:1）；
- 是否关注（大库先勾选关注的表）。

存储：`data_dictionary` 表，按数据源与对象键（`table` / `table.column`）存条目；
自动骨架与人工层分开列，刷新结构时**人工层不丢**。

注入策略：不整份进上下文。`describe_data_source` 先给关注表的清单与一句话说明；
模型再按需取具体表的列与字典条目。超过 60 张关注表时，用现有 RAG 检索按问题挑表。

样例值：只进字典缓存，**不进日志、运行记录、通知**；设置页可关闭抓取。

### 3.2 指标定义

`metrics` 表：`name`（如"销售额"）、`data_source_id`、`sql_fragment`（如 `SUM(o.paid_amount - o.refund_amount)`）、
`grain`（订单 / 客户 / 日）、`notes`（口径说明：含税、不含运费、剔除测试账号）、`source`（用户手填 / 从确认查询提取）。

技能规则：问题里出现未定义的指标词，先 `ask_user` 确认口径，再把确认结果存为指标。
已定义的指标直接复用，回复里注明"按已定义的口径：…"。

### 3.3 两段式：查询方案 → SQL

**第一段**输出结构化的查询方案（纯数据，有类型定义，可测）：

```
目标：每个客户 2026 年 8 月的销售额与订单数
表：orders（事实，时间基准 paid_at）、customers（维度）
连接：orders.customer_id → customers.id（N:1）
过滤：orders.status IN (已付款, 已退款)；paid_at ∈ [2026-08-01, 2026-09-01)
粒度：客户
指标：销售额 = 按已定义指标；订单数 = COUNT(DISTINCT orders.id)
排序 / 上限：销售额降序，前 100
未确定：是否剔除测试账号？
```

上面是内部表示。**给用户看的是它的业务语言渲染**，用字典里的业务名，不出现表名、列名、连接、`COUNT(DISTINCT)`：

> 我准备这样统计：**8 月**（按付款日期）每位客户的**销售额**和**订单数**，只算已付款和已退款的订单，
> 按销售额从高到低取前 100 位。有一点要确认：要不要把测试账号剔除？

经 `ask_user` 确认（方案无"未确定"项且与已有命名查询一致时跳过确认）。

**第二段**才从方案生成 SQL。SQL 与方案一起保存；执行结果里附方案的业务语言摘要，用户核对的是方案不是 SQL。

### 3.4 校验器与修复循环

校验器（纯函数）执行前必须通过：

- 只允许一条语句；去掉尾部分号后不得再出现分号；不含注释。
- 首个关键字只能是 `SELECT` / `WITH`；`WITH` 主体必须是 `SELECT`。
- 黑名单关键字按词边界匹配：`INSERT UPDATE DELETE REPLACE DROP ALTER CREATE TRUNCATE GRANT REVOKE CALL LOAD_FILE OUTFILE DUMPFILE HANDLER LOCK`。
- 无 `LIMIT` 的自动追加（默认 500，上限 5000）。
- 警告级（不拒绝，但要求方案说明）：JOIN 后直接聚合且无 DISTINCT / 无分组子查询。

校验器是**保守的拒绝器**，不是解析器：宁可拒绝一条合法的复杂查询让模型改写。

修复循环：校验通过 → `EXPLAIN` → 报错则把错误原文回给模型改写（最多 3 轮）→
估算行数超阈值（默认 200 万）先问用户缩小范围 → 执行。三轮仍失败，如实报告最后一次错误，不再尝试。

### 3.5 执行与可核对的结果

- 连接层：`mysql2`，会话 `SET SESSION TRANSACTION READ ONLY`，`SET time_zone` 按数据源配置，
  `utf8mb4`，30 秒超时，可取消。设置页"测试连接"时探测账号是否有写权限：**用 `SHOW GRANTS FOR CURRENT_USER()` 解析**，含 `ALL`、`INSERT`、`UPDATE`、`DELETE`、`DROP` 等任一即标"⚠ 该账号有写权限，建议换只读账号"。不做"试插入再回滚"——那会触发触发器、消耗自增值、写 binlog。
- `run_sql_query` 返回：列名与类型、行数、前 20 行、方案摘要、SQL、耗时；**完整结果写成工作区 `.csv` 产物**。
  其中 SQL 与耗时是给运行记录和开发者视图的，**模型的回复里不得复述 SQL**（3.11）。
- 每份产物带来源：Excel 加 `来源` 工作表（数据源、方案、SQL、时间、行数）；图表 SVG 加 `<desc>`。
- 结果不进上下文：模型只见前 20 行；要全量就读产物。

### 3.6 学习循环

- 用户确认"对，就是这个"后，`save_named_query` 保存：问题、方案、SQL、口径说明、数据源。
- 下一次提问，按问题相似度检索前 3 条命名查询作为示例注入（用现有 RAG 的向量检索），
  这是让模型"越来越懂业务"最有效的一招。
- 用户的纠正（"要含退款"）写回指标定义或字典条目，并进记忆候选。
- 命名查询可重跑、可定时。

**命名查询是示例与模板，不是触发器；存的是做法，不是结果。** 用户上一次的实现败在这里：
"工时"两个字命中预设就直接回放当时存下的东西，之后改年月也不生效。本计划用四条规则排除这种情况：

1. **结果从不保存**。`query_runs` 只存产物路径与统计；命名查询只存方案与 SQL。每一次提问都重新执行，
   没有任何路径能把"上次的结果"当成"这次的答案"返回。
2. **字面量参数化**。保存时把方案里的时间范围、过滤值等槽位值抽成参数，SQL 里对应位置是占位符
   （`paid_at >= {{time_from}} AND paid_at < {{time_to}}`）。保存的是"看工时的方式"，不是"看 2025 年 3 月工时"。
3. **复用时槽位一律取自当前问题**。命名查询提供的是方案的形状（指标口径、粒度、连接、过滤的种类）；
   时间范围、过滤值从这次的问题填。当前问题没给时间范围，按 3.12 的规则**问**，
   而不是沿用模板里上次的值——旧模板的字面量永远不是默认来源，只有记忆里的习惯（"默认看本月"）才是。
4. **相似度不是命中即用**。检索到的命名查询作为示例进入上下文，模型仍然要产出一份新方案；
   只有当新方案与某条命名查询**所有槽位都相同**时才跳过确认直接执行，且回复里注明
   "按你上次看工时的方式，换成 2026 年 8 月"，让用户看到复用了什么、改了什么。

评测集（3.7）加一组固定断言：同一指标换年月、换过滤条件、换粒度，三次提问必须各自得到对应的新结果，
方案摘要里的时间范围与当前问题一致；命名查询存在的情况下，缺时间范围的问题仍会追问。

### 3.7 评测集

`docs/p7-eval/` 下首轮维护用户给出的 10 个真实问题，每个带：问题原文、期望的方案要点、期望结果的校验方式
（行数、某个汇总值、或与命名查询一致）。后续从真实使用中自然增补，不为凑数编问题。`pnpm test:p7:eval` 对真实库跑一遍，输出部分自动指标；方案槽位、汇总值与业务答案仍须人工核对，不能仅凭脚本通过率宣称正确。

新增 migration：

### 3.9 工具与技能

| 工具 | 契约 | 说明 |
|---|---|---|
| `list_data_sources` | 只读 | |
| `describe_data_source` | 只读 | 表清单 / 指定表的列与字典条目 / 指标列表 |
| `propose_query_plan` | 只读 | 输入问题，输出结构化方案（3.3）；不发请求 |
| `run_sql_query` | `risk: 'medium'`、幂等、`evidence: 'output'` | 参数：`source`、`plan`、`sql`、`max_rows?`；校验、EXPLAIN、执行、产物 |
| `save_named_query` / `run_named_query` | `LOCAL_UPSERT_CONTRACT` / 同 `run_sql_query` | 学习与重跑 |
| `update_data_dictionary` | `LOCAL_UPSERT_CONTRACT` | 写人工层与指标；用户确认后才调用 |

`run_sql_query` 的确认弹窗显示目标数据源与**方案的业务语言摘要**；SQL 折叠在"查看执行详情"里，默认收起。
新增预览类型 `kind: 'query-plan'`，与 `text-diff` / `cell-changes` 并列。`risk: 'medium'` 走用户的权限策略，不强制每次确认。

技能 `data-query`：理解 → `describe_data_source` → 指标与口径追问（P6）→ `propose_query_plan` →
方案确认 → SQL → `run_sql_query` → 用户核对 → `save_named_query` → 导出。

### 3.10 设置页

设置 → 数据源：新增 / 编辑 / 删除；测试连接（连通、写权限探测、表数量）；刷新骨架；
关注的表；样例值开关；**字典编辑器**（按表列出，可填业务名、说明、枚举、时间基准列、合法连接）；指标列表；
**开发者视图开关**（默认关。开启后对话里的结果卡片可展开 SQL、耗时、EXPLAIN 摘要；关闭时这些只在运行记录里可查）。

### 3.11 表现层：业务语言优先

这是与"只读"同级的硬约束，不是界面美化。规则：

- **对话里默认不出现** SQL、表名、列名、JOIN、聚合函数、EXPLAIN、行数估计、数据库错误原文。
- 方案、追问、确认弹窗、结果摘要、错误说明，全部用字典里的**业务名**与日常语言写。字典没有业务名的表列，
  先用说明字段；两者都没有，模型应在方案里标"未确定"并问用户"这个数据叫什么"，顺手补进字典。
- **回复先给答案**：一两句话说结论（"8 月销售额最高的是 A 公司，12.3 万元，共 41 单"），然后是表或图，最后一句说产物在哪。
  不解释怎么算的，除非用户问；用户问了，用方案的业务语言说，仍不给 SQL。
- **追问用业务语言带选项**："销售额要不要算上已退款的订单？"而不是"status 是否包含 3？"。
- **错误翻译**：数据库报错先落运行记录，对用户说的是"没有找到'退款金额'这项数据，可能字典里还没登记"这类话。
  与稳定提示词"必须引用真实错误"的规则不冲突：真实错误在运行记录里可查，对话里给的是它的业务语言解释，
  且明确说"详情在运行记录"。
- **开发者视图**是唯一例外，默认关闭；开启的是使用者自己，不是模型。
- 评测集（3.7）对每个问题的回复增加一条断言：非开发者视图下**不含 SQL 关键字与表名列名**。

### 3.12 从笼统到可执行：信息收集循环（P6 在本阶段的用法）

用户的问题常常是"看看最近卖得怎么样"。这种问题无法直接变成方案，**这正是 P6 追问机制的用武之地**：
先收集信息，够了再出结果。规则要写死，否则模型要么乱猜、要么问个没完。

**一个方案要成立，五个槽位必须有值：**

| 槽位 | 例子 | 默认来源（按顺序找，找到就不问） |
|---|---|---|
| 指标 | 销售额 / 订单量 / 客户数 | 问题原文 → 已定义指标 → 记忆（"我说销售额都指含税"）→ 相似命名查询 |
| 时间范围 | 本月 / 最近 30 天 / 8 月 | 问题原文 → 记忆里的习惯 → 相似命名查询 |
| 粒度 | 按天 / 按客户 / 按部门 | 问题原文 → 相似命名查询 → **默认整体汇总** |
| 范围与过滤 | 只看华东 / 剔除测试账号 | 问题原文 → 记忆 → 相似命名查询 → **默认不过滤** |
| 排序与数量 | 前 10 / 全部 | 问题原文 → **默认按指标降序前 20** |

前两个槽位没有值**必须问**，后三个有默认值可以不问。

**问的方式**：一次一个槽位，业务语言带选项，选项来自字典与指标（"你想看的是销售额、订单量还是客户数？"），
选项里始终有"其他"。最多问 **2 个**问题；两个之后仍不完整，就用默认值**先给一版**，
并在结果后面说明用了哪些默认口径、可以怎么调（"我先按含税销售额、最近 30 天、整体汇总给你看。要按部门拆开或换时间范围，直接说。"）。

**为什么不问满五个**：探索式的问题用户自己也没想清楚，看到第一版结果才知道要改什么。
先给一版再迭代，比一口气问五个问题体验好得多，也更像"懂得思考"。

**迭代不重来**：用户说"再按部门分一下"，是在已确认的方案上改粒度槽位，其余槽位不变，也不再确认整份方案；
只在改动涉及新的未定义口径时才追问。方案是有状态的，命名查询保存的是最后一版。

**记忆的作用**：用户回答过的口径（"销售额算含税的"）作为记忆候选，确认后进入长期记忆；
下次同一槽位直接从记忆填，回复里注明"按你之前说的含税口径"。这是"越用越懂你"的具体机制之一，另一个是 3.6 的命名查询。

**评测集**（3.7）首轮 10 题里要有至少 4 个笼统问题，断言：追问不超过 2 次；追问用业务语言带选项；
两次后给出带默认口径说明的结果；用户补充一句后能在原方案上改而不是重来。

### 3.13 更准、更快的额外杠杆（2026-09-14 补充）

在 12 条对策之上，再加四条"更准"、三条"更快"。它们改变了 P7.2 的实现方式，见第 4 节。

**更准**

1. **方案编译器（核心变更）**。常见形状的 SQL 由确定性编译器从方案生成，模型只填槽位：
   - 支持的形状：一张事实表 + 若干维度表（按字典里的合法连接）+ 过滤 + 分组 + 指标（按指标定义的 SQL 片段）+ 排序 + 上限 + **对比周期**（同比 / 环比作为方案的一个槽位，编译成两段查询再合并）。
   - 编译器保证：时间范围左闭右开；粒度用"先按事实表粒度聚合、再连维度"避免连接放大；`LIMIT` 必加；只产生 `SELECT`。
   - 方案表达不了的问题（窗口函数、递归、复杂子查询）走**逃生口**：模型直接写 SQL，经校验器与修复循环，方案里标 `raw_sql: true`，运行记录可查。评测集统计逃生口比例，越低越好。
   - 效果：语法错误、时间口径、连接放大三类问题在常见形状里**结构性消失**，而不是靠模型小心。
2. **值定位**。字典对枚举型文本列（去重值 ≤ 200）缓存取值表，随骨架刷新。问题里的字面量（"华东"、"已退款"）先在取值表里匹配，
   命中才进过滤并在方案里注明"华东 = 区域"。高基数列（姓名、单号）不建表，字面量出现时对候选列做 `LIKE` 探测（限 3 列、各 1 秒）。
3. **结果自检**。主查询后并行跑两个便宜查询：(a) 分组合计 vs 整体合计，不等即连接放大；(b) 实际覆盖的最小 / 最大日期 vs 方案时间范围。
   任一不过，结果不给用户，先说明"合计对不上，可能重复计算了，正在改"。自检本身也是只读 `SELECT`。
4. **字典自举**。骨架抓取读取 MySQL 的 `TABLE_COMMENT` / `COLUMN_COMMENT` 作为业务名与说明的初始值；
   对枚举列，由模型根据列名、注释、取值表**提议**枚举含义，用户确认后写入人工层。目标是把"填字典半小时"压到十分钟。

**更快**

5. **减少模型轮次**。编译器省掉"写 SQL"一轮；槽位全部命中且与命名查询一致时零追问；方案与结果摘要流式输出。
   常规问题的路径：一轮模型 → 一次 `EXPLAIN` → 一次执行（自检并行）。
6. **定时物化**。重报表由命名查询夜里定时跑成文件（P7.5），白天秒开且不占库。这是唯一允许的"预先算好"，产物上标明数据截至时间。
7. **连接池与本地缓存**。连接复用；结构卡片、取值表、指标本地缓存，按手动刷新或每日刷新。

**明确不做的提速手段**：**不缓存查询结果**。上一次的痛点正是拿到旧结果，任何结果缓存都会重新引入它；
速度只从 5、6、7 来。也不把"换更强模型"当首要手段：有编译器后模型只填槽位，是否换模型由评测集决定。

## 11. 落地细节（2026-09-14 复核）

### 11.1 查询方案的数据结构（P7.0）

`src/datasources/query-plan.ts`，编译器与渲染器的唯一输入：

```ts
interface QueryPlan {
  sourceId: string;
  fact: { table: string };                                   // 事实表（字典里标为真源）
  dimensions: Array<{ table: string; join: string }>;        // join 引用字典里的合法连接 id
  timeRange?: { column: string; from: string; to: string };  // 左闭右开，ISO 日期
  filters: Array<{ column: string; op: 'eq' | 'in' | 'neq' | 'gte' | 'lte' | 'like'; values: string[] }>;
  grain: string[];                                           // 分组列（业务名解析后的物理列）
  metrics: Array<{ name: string; fragment: string }>;        // 来自指标定义；未定义指标不得出现在方案里
  compare?: { kind: 'yoy' | 'mom' };                         // 同比 / 环比
  orderBy?: { metric: string; direction: 'asc' | 'desc' };
  limit: number;                                             // 1–5000
  unresolved: Array<{ slot: '指标' | '时间范围' | '粒度' | '范围过滤' | '排序数量'; question: string; options?: string[] }>;
  rawSql?: string;                                           // 逃生口：方案表达不了时模型直接写；有它则跳过编译器
}
```

`unresolved` 非空时不进编译器，先按 3.12 追问。`propose_query_plan` 的产出必须通过这个类型的校验（zod 或手写校验，与 `ipc-validation` 风格一致）。

### 11.2 编译器（P7.0）

`compileQueryPlan(plan, dictionary): { sql: string; selfChecks: string[] }`，纯函数：

- 先按事实表粒度聚合成 CTE：`WITH f AS (SELECT <grain 里属于事实表的列>, <metrics> FROM fact WHERE <timeRange> AND <filters on fact> GROUP BY …)`，再 `JOIN` 维度表取展示列。一对多连接因此不会放大指标。
- `compare` 生成第二段同结构 CTE（时间范围平移一年或一月），最终 `SELECT` 里并列本期、上期、差值与增幅。
- 所有标识符用反引号，字面量用参数占位（`?`），执行时走 `mysql2` 的参数绑定，不拼字符串。
- `selfChecks`：两条只读 SQL——整体合计（同一过滤、无分组）与实际日期覆盖（`MIN/MAX` 时间列）。仅编译路径有；`rawSql` 路径没有自检，回复里注明"这个结果未经自动核对"。
- 逃生口 `rawSql`：过校验器；外层统一包一层 `SELECT * FROM (<sql>) AS _q LIMIT n`，不解析内部 `LIMIT`。

### 11.3 连接层（P7.1）

- `src/datasources/mysql.ts` 用 `mysql2/promise` 连接池（每数据源最多 3 连接）。每个连接建立时执行：
  `SET SESSION TRANSACTION READ ONLY`、`SET SESSION max_execution_time = 30000`、`SET NAMES utf8mb4`；
  `SET time_zone = ?` 只在 `options_json.timeZone` 明确设了值时执行（§10：用户不确定库存的是什么时间，默认跟随服务器）。
- `query(sql, params, { maxRows, signal })`：用 `connection.query` 的流式接口按行计数，超过 `maxRows` 即 `destroy()` 连接（不能优雅取消时以断连为准）；`signal` 触发同样断连。
- `fetchSchema`：`information_schema.TABLES / COLUMNS / KEY_COLUMN_USAGE`，一并读 `TABLE_COMMENT` / `COLUMN_COMMENT`。
- `fetchValues`：只对类型为 `enum` 或 `char/varchar(≤ 64)` 且表行数估计 ≤ 500 万的列执行 `SELECT col FROM t GROUP BY col LIMIT 201`，每列 2 秒超时；201 行即标高基数不存。只在用户点"刷新"时跑。
- 密码存储 `protectSecret`，与转写凭证一致；`options_json` 含 `ssl`（默认 false，公网主机未开时提醒）、`timeZone`（缺省跟随服务器）、`sampleValues`、`focusTables`。
- `ping` 顺带返回时区探测结果（global / session / system 时区、`NOW()` 与 `UTC_TIMESTAMP()` 之差），设置页原样展示。

### 11.4 命名查询的相似检索（P7.3）

不新建索引体系：保存时用 `src/rag/embedding.ts` 的 `embedText(question)` 得到向量，存 `named_queries.question_embedding`（BLOB，float32）。
提问时对同一数据源的命名查询在 JS 里做余弦相似度（几百条量级），取 ≥ 0.80 的前 3 条作为示例注入；没有嵌入模型配置时退化为关键词重叠，回复不受影响。

### 12.2 P7.1 MySQL 连接器、设置页与字典编辑器（2026-09-15）

按 §11.3 走，`mysql2@3.24.4` 提升为直接依赖（vite externals、打包白名单含它的 7 个间接依赖）。三处与计划不同或计划没写的：

- **取值表的候选列多了 tinyint / smallint**。§11.3 只写了 `enum` 与 `char/varchar(≤ 64)`，但 3.13.4 要模型提议枚举含义的
  正是 `status tinyint` 这类状态码列，没有取值表就无从提议。整数列的 `GROUP BY` 同样受 2 秒超时与 500 万行上限约束。
- **写权限探测只看 `SHOW GRANTS`，不做任何写尝试**（哪怕在只读事务里）。出现 `ALL PRIVILEGES` / `INSERT` / `UPDATE` /
  `DELETE` / `DROP` 等任一写类权限即判"可写"并在设置页标出；账号通过角色授权时权限看不出来，标为"探测不了"并提醒。

- **会话初始化在连接第一次被取出时做**，而不是 `pool.on('connection')`：promise 池的事件给的是回调式连接，
  没法在上面等 `SET` 完成再放行。`fresh` 标记保证每条物理连接只初始化一次。`max_execution_time` 不存在（MariaDB）时忽略，
  靠客户端超时与断连兜底。

### 12.3 P7.2 方案、SQL 与修复循环（2026-09-15，代码完成，基线待真实库）

用户暂时连不上真实库，先把代码做完并用假连接层测好；评测集基线（`pnpm test:p7:eval`）等用户在设置里连上库、刷新结构后再跑。
与计划不同或计划没写的四处：

- **加了"清单模式"**（`QueryPlan.select`）。评测集 10 个问题里有 5 个是"有哪些项目没打尾款"、"员工今天都有什么任务"这类列行不聚合的问题，
  §11.1 的方案只有聚合形状，这些问题会全部掉进逃生口，逃生口比例必然超过三成的停线条件。清单模式：`select` 列 `表.列`、
  不带指标与分组，编译成 `SELECT … FROM 事实表 LEFT JOIN 维度 WHERE … ORDER BY 时间列 DESC LIMIT n`；自检是同过滤的总行数与日期覆盖。
- **值定位只做字典内匹配，LIKE 探测推到 P7.3**。`propose_query_plan` 按 §3.9 是"不发请求"的，3.13.2 的高基数列 LIKE 探测要连库，
  两者冲突时以"不发请求"为准：精确命中 → 枚举含义反查（"已付款"→ 2）→ 二元组相似度唯一命中（"华东区"→"华东"，回复里注明）→
  否则变成一条带候选选项的"范围过滤"追问。没有取值表的列原样保留。
- **大库挑表第一版用关键词二元组打分，不用向量检索**。§3.1 说"用现有 RAG 检索按问题挑表"，但字典条目还没进向量库（P7.3 才做命名查询的向量），
  先用表名、业务名、说明、列注释的二元组重叠打分，命中不足时用关注表补齐；P7.3 接向量后再换。
- **修复循环由模型驱动、工具计数**。工具拿到数据库报错后返回"数据库拒绝了这个查询（第 N 次）+ 原文"，模型带 `attempt` 改写重试；
  第 3 次仍失败返回给用户的翻译文案并明确"不再重试"。EXPLAIN 行数估计取各表 rows 的乘积，超过 200 万先请用户缩小范围。

### 12.5 P7.4 导出与图表（2026-09-15）

- 工具 `export_query_result`（`WORKSPACE_WRITE_CONTRACT`）：输入 `run_sql_query` 落下的 CSV 路径，`format: xlsx | chart`。
- **Excel**：工作表「结果」按列分型——全是数字（不含前导零的编号）的列写数字、全是 ISO 日期的列写日期（以 UTC 分量构造 `Date`，
  Excel 没有时区，墙上时间与文本一致，`numFmt yyyy-mm-dd hh:mm:ss`）、其余文本；工作表「来源」两列（项 / 值）：数据源、方案的业务语言摘要、
  SQL、执行时间、行数。方案与 SQL 从 `query_runs` 按产物路径找回（`getQueryRunByArtifactPath`），找不到就写"未知"。SQL 出现在这里是给核对用的，与 3.11 不冲突。
- **图表**：复用 `gen_chart`（SVG + PNG），`<desc>` 写 CSV 路径、数据源与执行时间；类目超过 50 个提示"按更粗的粒度重查"，数值列不是数字列拒绝。
- 固定样本（`export-and-rerun.test.ts`）：数字列不变文本（`007` 保持文本、`120.5` 成数字）、日期列格式、来源页五项、类目超限提示。
- CSV 读回：`parseCsv`（RFC 4180，BOM）、`classifyCsvColumn`、`isoToExcelDate`。

### 12.6 P7.5 命名查询定时重跑（2026-09-15，代码完成）

- 工具 `run_named_query`：与 `run_sql_query` 同一条执行路径（`executePreparedPlan` 抽成共用：预览 → 确认 → EXPLAIN → 自检并行 → CSV → 查询记录）。
