# P7 · 数据源查询实施计划

> 计划验收入口：逐阶段补齐 `pnpm test:p7`，以及第 3 节的**评测集**通过率
>
> 阶段编号沿用 P 系列。P7 是已取消的 P2（外部连接器）的收窄版：只连 MySQL、只读、
> 把"我说想法 → 它组 SQL → 出 Excel 或图表"跑通，并且**越用越准**。依赖 P5 的产出工具与 P6 的追问机制。

当前状态（2026-09-14）：**未开工**。本文是开工前的契约，不是验收记录。

**用户已明确的范围（2026-09-14）**：第一版只连 **MySQL**；SQL Server 与其它数据库搁置，等真实需求。
用户此前做过类似功能，**效果不好**——第 2 节先回答"这次为什么会不一样"。

---

## 1. 目标与边界

**要解决的**：用户用自己的业务语言提问，助理读懂库结构与业务口径、口径不明时先问、
生成只读 SQL、校验后执行、把结果变成 Excel 或图表，并把每一次确认过的问答沉淀下来，
让下一次同类问题更准。

**不解决的**：任何写库操作、跨库联查、通用 SQL 编辑器、MySQL 之外的数据库。见第 8 节。

**蓝图约束**："不开放高危系统权限"。外部数据库对本项目是高危面，因此**连接层就只读**，
不靠提示词约束模型不写。

---

## 2. 为什么"自然语言转 SQL"通常效果不好，这次怎么做

这类功能失败的原因高度集中。逐条列出，并写明本计划对应的机制。
**每一条机制都是本计划的验收项**，不是愿景。

| # | 失败原因 | 典型表现 | 本计划的机制 |
|---|---|---|---|
| 1 | **模型只看到表结构，看不到业务含义** | 列名叫 `f_amt1`、`status` 是 1/2/3；模型猜错表、猜错列 | **数据字典**（3.1）：表和列的说明、枚举值含义、哪张表是真源、哪些连接是合法的。自动抓一份骨架，**由用户和确认过的查询逐步补全** |
| 2 | **业务口径没有定义** | "销售额"每次算法都不一样 | **指标定义**（3.2）：命名指标带 SQL 片段与口径说明；未定义的指标必须先问（P6） |
| 3 | **直接从问题跳到 SQL** | 用户看到一段 SQL，看不懂对不对 | **两段式**（3.3）：先出一份人能读懂的**查询方案**（用哪些表、怎么连、按什么口径、什么粒度、什么时间基准），用户确认后再生成 SQL |
| 4 | **结果对不对没人知道** | SQL 跑出来一个数，用户无从核对 | **可核对的结果**（3.5）：每次执行返回行数、样例、方案摘要与 SQL；产物带来源；每个数字都能追到方案 |
| 5 | **连接放大** | 一对多 JOIN 后再 SUM，金额翻倍 | 字典记录外键基数；方案里必须声明**粒度**；校验器对"JOIN 后直接聚合且无 DISTINCT / 无子查询分组"给出警告并要求方案说明 |
| 6 | **时间口径混乱** | 时区、日期与日期时间、"上个月"按哪天算 | 字典里为每张事实表标注**时间基准列**；工具注入当前日期与连接时区；日期范围一律左闭右开；相对时间必须在方案里写成绝对区间 |
| 7 | **大库塞不进上下文** | 几百张表全给模型，它挑错 | **按需取表**（3.1）：先给表清单与一句话说明，模型再取具体表；字典可用现有 RAG 检索 |
| 8 | **SQL 错了就完** | 语法错、函数名错、字段名错 | **修复循环**（3.4）：先 `EXPLAIN`，报错回给模型改写，最多 3 轮；仍失败就如实告诉用户哪里不对 |
| 9 | **慢查询拖死** | 全表扫描、超时 | `EXPLAIN` 估算行数超阈值先问用户缩小范围；30 秒超时；可取消；行数上限 |
| 10 | **不会从纠正里学习** | 用户说"不对，要含退款"，下次照错 | **学习循环**（3.6）：确认过的问答存为命名查询并作为相似问题的示例注入；纠正写回字典与指标；口径进记忆候选 |
| 11 | **没有度量，不知道有没有变好** | 改了提示词，感觉好一点，说不清 | **评测集**（3.7）：20 个真实问题带期望结果，每次改动后跑，通过率是硬指标 |
| 12 | **用户被迫看 SQL 和术语** | 回复里大段 SQL、表名、字段名；开发者能看懂，别人不能 | **业务语言优先**（3.11）：SQL 与表名是执行细节，默认不出现在对话里；方案、追问、确认、结果、错误全部用业务语言；技术细节收在"详情"里给开发者 |

用户确认（2026-09-14）：**上一次这 12 条全都发生过**。其中第 12 条是产品层面的：
功能再准，用户看到的是 SQL 就不会用。因此本计划把"业务语言优先"列为与"只读"同级的硬约束，
第 3.11 节单独规定，停线条件里也有它。

## 3. 设计决定

### 3.1 数据字典（核心资产）

连接成功后自动生成**骨架**：表、列、类型、主键、外键、行数估计、每列前 3 个非空样例值（文本截断 40 字）。
骨架之上是**人工层**，每张表、每列可填：

- **业务名**（表：`orders` → "订单"；列：`paid_amount` → "实付金额"）。这是 3.11 的基础：对话里出现的永远是业务名，不是表名列名；
- 说明（一句话）；
- 枚举值含义（`status: 1=待付款 2=已付款 3=已退款`）；
- 是否真源（同一业务有多张表时指明该用哪张）；
- 时间基准列（事实表必填，见 2.6）；
- 合法连接（`orders.customer_id → customers.id`，基数 N:1）；
- 是否关注（大库先勾选关注的表）。

存储：`data_dictionary` 表，按数据源与对象键（`table` / `table.column`）存条目；
自动骨架与人工层分开列，刷新结构时**人工层不丢**。

注入策略：不整份进上下文。`describe_data_source` 先给关注表的清单与一句话说明；
模型再按需取具体表的列与字典条目。超过 60 张关注表时，用现有 RAG 检索按问题挑表。

样例值：只进字典缓存，**不进日志、运行记录、通知**；设置页可关闭抓取。

### 3.2 指标定义

`metrics` 表：`name`（如"销售额"）、`data_source_id`、`sql_fragment`（如 `SUM(o.paid_amount - o.refund_amount)`）、
`grain`（订单 / 客户 / 日）、`notes`（口径说明：含税、不含运费、剔除测试账号）、`source`（用户手填 / 从确认查询提取）。

技能规则：问题里出现未定义的指标词，先 `ask_user` 确认口径，再把确认结果存为指标。
已定义的指标直接复用，回复里注明"按已定义的口径：…"。

### 3.3 两段式：查询方案 → SQL

**第一段**输出结构化的查询方案（纯数据，有类型定义，可测）：

```
目标：每个客户 2026 年 8 月的销售额与订单数
表：orders（事实，时间基准 paid_at）、customers（维度）
连接：orders.customer_id → customers.id（N:1）
过滤：orders.status IN (已付款, 已退款)；paid_at ∈ [2026-08-01, 2026-09-01)
粒度：客户
指标：销售额 = 按已定义指标；订单数 = COUNT(DISTINCT orders.id)
排序 / 上限：销售额降序，前 100
未确定：是否剔除测试账号？
```

上面是内部表示。**给用户看的是它的业务语言渲染**，用字典里的业务名，不出现表名、列名、连接、`COUNT(DISTINCT)`：

> 我准备这样统计：**8 月**（按付款日期）每位客户的**销售额**和**订单数**，只算已付款和已退款的订单，
> 按销售额从高到低取前 100 位。有一点要确认：要不要把测试账号剔除？

经 `ask_user` 确认（方案无"未确定"项且与已有命名查询一致时跳过确认）。

**第二段**才从方案生成 SQL。SQL 与方案一起保存；执行结果里附方案的业务语言摘要，用户核对的是方案不是 SQL。

### 3.4 校验器与修复循环

校验器（纯函数）执行前必须通过：

- 只允许一条语句；去掉尾部分号后不得再出现分号；不含注释。
- 首个关键字只能是 `SELECT` / `WITH`；`WITH` 主体必须是 `SELECT`。
- 黑名单关键字按词边界匹配：`INSERT UPDATE DELETE REPLACE DROP ALTER CREATE TRUNCATE GRANT REVOKE CALL LOAD_FILE OUTFILE DUMPFILE HANDLER LOCK`。
- 无 `LIMIT` 的自动追加（默认 500，上限 5000）。
- 警告级（不拒绝，但要求方案说明）：JOIN 后直接聚合且无 DISTINCT / 无分组子查询。

校验器是**保守的拒绝器**，不是解析器：宁可拒绝一条合法的复杂查询让模型改写。

修复循环：校验通过 → `EXPLAIN` → 报错则把错误原文回给模型改写（最多 3 轮）→
估算行数超阈值（默认 200 万）先问用户缩小范围 → 执行。三轮仍失败，如实报告最后一次错误，不再尝试。

### 3.5 执行与可核对的结果

- 连接层：`mysql2`，会话 `SET SESSION TRANSACTION READ ONLY`，`SET time_zone` 按数据源配置，
  `utf8mb4`，30 秒超时，可取消。设置页"测试连接"时探测账号是否有写权限（事务内试探后回滚），有则标"⚠ 建议换只读账号"。
- `run_sql_query` 返回：列名与类型、行数、前 20 行、方案摘要、SQL、耗时；**完整结果写成工作区 `.csv` 产物**。
  其中 SQL 与耗时是给运行记录和开发者视图的，**模型的回复里不得复述 SQL**（3.11）。
- 每份产物带来源：Excel 加 `来源` 工作表（数据源、方案、SQL、时间、行数）；图表 SVG 加 `<desc>`。
- 结果不进上下文：模型只见前 20 行；要全量就读产物。

### 3.6 学习循环

- 用户确认"对，就是这个"后，`save_named_query` 保存：问题、方案、SQL、口径说明、数据源。
- 下一次提问，按问题相似度检索前 3 条命名查询作为示例注入（用现有 RAG 的向量检索），
  这是让模型"越来越懂业务"最有效的一招。
- 用户的纠正（"要含退款"）写回指标定义或字典条目，并进记忆候选。
- 命名查询可重跑、可定时。

**命名查询是示例与模板，不是触发器；存的是做法，不是结果。** 用户上一次的实现败在这里：
"工时"两个字命中预设就直接回放当时存下的东西，之后改年月也不生效。本计划用四条规则排除这种情况：

1. **结果从不保存**。`query_runs` 只存产物路径与统计；命名查询只存方案与 SQL。每一次提问都重新执行，
   没有任何路径能把"上次的结果"当成"这次的答案"返回。
2. **字面量参数化**。保存时把方案里的时间范围、过滤值等槽位值抽成参数，SQL 里对应位置是占位符
   （`paid_at >= {{time_from}} AND paid_at < {{time_to}}`）。保存的是"看工时的方式"，不是"看 2025 年 3 月工时"。
3. **复用时槽位一律取自当前问题**。命名查询提供的是方案的形状（指标口径、粒度、连接、过滤的种类）；
   时间范围、过滤值从这次的问题填。当前问题没给时间范围，按 3.12 的规则**问**，
   而不是沿用模板里上次的值——旧模板的字面量永远不是默认来源，只有记忆里的习惯（"默认看本月"）才是。
4. **相似度不是命中即用**。检索到的命名查询作为示例进入上下文，模型仍然要产出一份新方案；
   只有当新方案与某条命名查询**所有槽位都相同**时才跳过确认直接执行，且回复里注明
   "按你上次看工时的方式，换成 2026 年 8 月"，让用户看到复用了什么、改了什么。

评测集（3.7）加一组固定断言：同一指标换年月、换过滤条件、换粒度，三次提问必须各自得到对应的新结果，
方案摘要里的时间范围与当前问题一致；命名查询存在的情况下，缺时间范围的问题仍会追问。

### 3.7 评测集

`docs/p7-eval/` 下维护 20 个真实问题，每个带：问题原文、期望的方案要点、期望结果的校验方式
（行数、某个汇总值、或与命名查询一致）。`pnpm test:p7:eval` 对真实库跑一遍，输出通过率。
**评测集在 P7.0 就开始攒**，先由用户给出 20 个他真正会问的问题；没有它，"效果好不好"没有答案。

### 3.9 工具与技能

| 工具 | 契约 | 说明 |
|---|---|---|
| `list_data_sources` | 只读 | |
| `describe_data_source` | 只读 | 表清单 / 指定表的列与字典条目 / 指标列表 |
| `propose_query_plan` | 只读 | 输入问题，输出结构化方案（3.3）；不发请求 |
| `run_sql_query` | `risk: 'medium'`、幂等、`evidence: 'output'` | 参数：`source`、`plan`、`sql`、`max_rows?`；校验、EXPLAIN、执行、产物 |

| `update_data_dictionary` | `LOCAL_UPSERT_CONTRACT` | 写人工层与指标；用户确认后才调用 |

`run_sql_query` 的确认弹窗显示目标数据源与**方案的业务语言摘要**；SQL 折叠在"查看执行详情"里，默认收起。
新增预览类型 `kind: 'query-plan'`，与 `text-diff` / `cell-changes` 并列。`risk: 'medium'` 走用户的权限策略，不强制每次确认。

技能 `data-query`：理解 → `describe_data_source` → 指标与口径追问（P6）→ `propose_query_plan` →
方案确认 → SQL → `run_sql_query` → 用户核对 → `save_named_query` → 导出。

### 3.10 设置页

设置 → 数据源：新增 / 编辑 / 删除；测试连接（连通、写权限探测、表数量）；刷新骨架；
关注的表；样例值开关；**字典编辑器**（按表列出，可填业务名、说明、枚举、时间基准列、合法连接）；指标列表；
**开发者视图开关**（默认关。开启后对话里的结果卡片可展开 SQL、耗时、EXPLAIN 摘要；关闭时这些只在运行记录里可查）。

### 3.11 表现层：业务语言优先

这是与"只读"同级的硬约束，不是界面美化。规则：

- **对话里默认不出现** SQL、表名、列名、JOIN、聚合函数、EXPLAIN、行数估计、数据库错误原文。
- 方案、追问、确认弹窗、结果摘要、错误说明，全部用字典里的**业务名**与日常语言写。字典没有业务名的表列，
  先用说明字段；两者都没有，模型应在方案里标"未确定"并问用户"这个数据叫什么"，顺手补进字典。
- **回复先给答案**：一两句话说结论（"8 月销售额最高的是 A 公司，12.3 万元，共 41 单"），然后是表或图，最后一句说产物在哪。
  不解释怎么算的，除非用户问；用户问了，用方案的业务语言说，仍不给 SQL。
- **追问用业务语言带选项**："销售额要不要算上已退款的订单？"而不是"status 是否包含 3？"。
- **错误翻译**：数据库报错先落运行记录，对用户说的是"没有找到'退款金额'这项数据，可能字典里还没登记"这类话。
  与稳定提示词"必须引用真实错误"的规则不冲突：真实错误在运行记录里可查，对话里给的是它的业务语言解释，
  且明确说"详情在运行记录"。
- **开发者视图**是唯一例外，默认关闭；开启的是使用者自己，不是模型。
- 评测集（3.7）对每个问题的回复增加一条断言：非开发者视图下**不含 SQL 关键字与表名列名**。

### 3.12 从笼统到可执行：信息收集循环（P6 在本阶段的用法）

用户的问题常常是"看看最近卖得怎么样"。这种问题无法直接变成方案，**这正是 P6 追问机制的用武之地**：
先收集信息，够了再出结果。规则要写死，否则模型要么乱猜、要么问个没完。

**一个方案要成立，五个槽位必须有值：**

| 槽位 | 例子 | 默认来源（按顺序找，找到就不问） |
|---|---|---|
| 指标 | 销售额 / 订单量 / 客户数 | 问题原文 → 已定义指标 → 记忆（"我说销售额都指含税"）→ 相似命名查询 |
| 时间范围 | 本月 / 最近 30 天 / 8 月 | 问题原文 → 记忆里的习惯 → 相似命名查询 |
| 粒度 | 按天 / 按客户 / 按部门 | 问题原文 → 相似命名查询 → **默认整体汇总** |
| 范围与过滤 | 只看华东 / 剔除测试账号 | 问题原文 → 记忆 → 相似命名查询 → **默认不过滤** |
| 排序与数量 | 前 10 / 全部 | 问题原文 → **默认按指标降序前 20** |

前两个槽位没有值**必须问**，后三个有默认值可以不问。

**问的方式**：一次一个槽位，业务语言带选项，选项来自字典与指标（"你想看的是销售额、订单量还是客户数？"），
选项里始终有"其他"。最多问 **2 个**问题；两个之后仍不完整，就用默认值**先给一版**，
并在结果后面说明用了哪些默认口径、可以怎么调（"我先按含税销售额、最近 30 天、整体汇总给你看。要按部门拆开或换时间范围，直接说。"）。

**为什么不问满五个**：探索式的问题用户自己也没想清楚，看到第一版结果才知道要改什么。
先给一版再迭代，比一口气问五个问题体验好得多，也更像"懂得思考"。

**迭代不重来**：用户说"再按部门分一下"，是在已确认的方案上改粒度槽位，其余槽位不变，也不再确认整份方案；
只在改动涉及新的未定义口径时才追问。方案是有状态的，命名查询保存的是最后一版。

**记忆的作用**：用户回答过的口径（"销售额算含税的"）作为记忆候选，确认后进入长期记忆；
下次同一槽位直接从记忆填，回复里注明"按你之前说的含税口径"。这是"越用越懂你"的具体机制之一，另一个是 3.6 的命名查询。

**评测集**（3.7）里要有至少 5 个笼统问题，断言：追问不超过 2 次；追问用业务语言带选项；
两次后给出带默认口径说明的结果；用户补充一句后能在原方案上改而不是重来。

## 4. 实施阶段

### P7.0 — 契约、校验器、字典与评测集（3 天）

- 校验器（3.4）纯函数与固定样本：合法 `SELECT` / `WITH` / 子查询；被拒的 `UPDATE`、多语句、注释绕过、`OUTFILE`、`CALL`；`LIMIT` 注入；JOIN 聚合警告。
- 查询方案的类型定义、渲染为文字的纯函数、从方案到 SQL 的映射规则（先做纯函数骨架，模型负责填空）。
- 字典与指标的数据结构、骨架生成的格式化纯函数（含截断规则）。
- 五张表的仓储。
- **评测集**：用户给出 20 个真实问题，先只写问题与期望要点，不需要能跑。
- 建立 `pnpm test:p7`。不发任何真实数据库请求。

**阶段出口**：校验器与方案渲染对固定样本有确定输出；评测集问题就位。

### P7.1 — MySQL 连接器、设置页与字典编辑器（3–4 天）

- `mysql2` 接入（加 vite externals 与打包白名单）；连接层接口 `connect / ping / probeWritable / fetchSchema / explain / query(sql, maxRows, timeout, signal)`。
- 设置页（3.10）含字典编辑器与指标列表；凭证加密。
- 真实验证：连用户的真实库，`ping`、写权限探测、骨架抓取；**用户花半小时填关键表的字典**——这一步不做，后面全是空谈。

**阶段出口**：真实库连通；关注表的字典有人工层；写权限账号被标出。

### P7.2 — 方案、SQL 与修复循环（3–4 天）

- `propose_query_plan`、`run_sql_query`、修复循环、EXPLAIN 阈值。
- `data-query` 技能，口径追问接 P6 的 `ask_user`。
- 评测集接真实库：`pnpm test:p7:eval` 跑出**基线通过率**。

**阶段出口**：评测集基线出来；至少一半问题一次通过；所有回复通过 3.11 的表现层断言。低于一半先补字典与指标，不改代码。

### P7.3 — 学习循环（2 天）

- 命名查询保存、相似检索示例注入、纠正写回字典与指标（3.6）。
- 评测集再跑：**通过率必须高于 P7.2 基线**，否则示例注入方式有问题。

### P7.4 — 导出与图表（1–2 天）

- 结果 → `gen_xlsx`（带来源工作表）→ `gen_chart`（P5.3）。
- 固定样本：数字列不变文本；日期列格式；类目超限提示聚合。

### P7.5 — 命名查询定时重跑（1 天）

- `run_named_query` 接 P3 定时任务；产物按日期命名；数据源被删时任务停用并提示。

### P7.6 — 回归与真实使用（2 天 + 观察）

- `pnpm test:p7`、`test:p7:eval`、全量、`typecheck`、`build`、`test:ui:strict`、`test:electron`。
- 两周真实使用：每个问题记录追问次数、方案是否需改、SQL 修复轮数、用户是否核对通过。评测集通过率每周记一次。

## 7. 为 SQL Server 与其它数据库留的口子

连接层接口（P7.1）按方言无关设计；校验器的黑名单与 `LIMIT` 注入按方言分文件。

## 8. 明确不做

- **不做任何写库**；校验器不给"确认后可写"留口子。
- **不做跨库联查**。
- **不做通用 SQL 编辑器 / 数据库管理界面**。
- **不连 SQL Server、PostgreSQL、Oracle 等**：见第 7 节。
- **不把结果全量注入上下文**。
- **不在日志、运行记录、通知里出现样例值与结果数据**。
- **不做交互式图表与仪表盘**。
- **不做本地的自然语言转 SQL 模型**：用当前对话模型 + 字典 + 指标 + 示例 + 校验器。
- **不跳过评测集**：没有通过率就不宣称"效果好"。

## 9. 推荐开工顺序与停线条件

建议顺序：**P7.0 → P7.1 → （等 P6.1）→ P7.2 → P7.3 → P7.4 → P7.5 → P7.6**。
P7.0 与 P7.1 可在 P5 / P6 进行中并行。

**开工前提**：用户先给 20 个真实问题（3.7），并愿意在 P7.1 花半小时填字典。这两件事不做，本阶段不开工。

出现以下任一情况立即停止扩大范围：

- 任何路径能把非 `SELECT` 语句发到数据库；
- 校验器为放行某条查询而加例外；
- 密码以明文出现在数据库、日志或渲染层；
- 结果数据或样例值进入日志、运行记录或通知；
- 权限策略为"确认"时未经确认执行了 SQL；
- 单次查询无上限、无超时或不可取消；
- 模型跳过方案直接给 SQL，或方案里有"未确定"项却没有问；
- 评测集通过率下降却继续加功能；
- 为了兼容第二种数据库而推迟字典、指标或学习循环；
- 非开发者视图下对话里出现了 SQL、表名、列名或数据库错误原文；
- 同一问题追问超过 2 次仍不给结果，或指标、时间范围缺失时不问就猜；
- 任何路径返回了保存的结果而不是重新执行；命名查询以字面量（具体年月、具体过滤值）被直接回放。
