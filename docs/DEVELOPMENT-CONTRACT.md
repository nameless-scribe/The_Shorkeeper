# The Shorekeeper 开发契约

> 版本：1.0.0
> 生效日期：2026-09-13
> 适用范围：本仓库的全部代码、界面、数据库、脚本、配置、测试与文档改动
> 规则入口：根目录 `AGENTS.md` 与 `.cursor/rules/project-development-contract.mdc`

## 1. 契约目标

所有改动必须同时守住四件事：**体验一致、数据安全、行为可信、可验证交付**。新功能不能只做到“能运行”；它还必须融入现有产品、遵守进程和数据边界、覆盖失败路径，并留下足够的测试与文档。

本文中：

- **必须**：合入或交付前不可省略；不满足即视为未完成。
- **应该**：默认遵守；偏离时必须在变更说明中记录理由与替代保障。
- **可以**：按需求选择，不构成验收门槛。

规则优先级为：安全与用户数据完整性 → 用户明确需求 → 本契约 → 模块专项文档 → 就近代码惯例。安全与数据完整性不得通过例外降级；发现其他冲突时先停止扩大改动，说明冲突并更新约定，不能静默选择一种实现。

## 2. 通用改动纪律

1. 修改前必须先阅读相邻实现、相关测试和专项文档，优先扩展现有模式，不平行发明第二套架构或组件体系。
2. 改动必须聚焦需求；不得顺手重写无关模块、格式化整仓或覆盖用户已有改动。
3. 新功能必须定义成功、空数据、加载、失败、取消/超时、重启恢复和数据兼容行为中与其有关的部分。
4. Bug 修复必须先解释根因，并新增能复现该根因的回归测试；不能只压制日志或吞掉异常。
5. 新依赖、公共抽象或跨层协议必须说明现有能力为什么不足。能复用当前依赖和小型本地实现时，不引入新运行时依赖。
6. 不提交真实密钥、`.env`、数据库、用户工作区、日志、构建产包或生成目录。完成前必须检查 `git status` 和 `git diff`。

## 3. UI 与交互一致性

### 3.1 视觉语言

1. 新界面必须以最接近的现有页面为基准；设置功能优先复用 `SettingsPageShell`、`SettingsIntro`、`SettingsSection`、`SettingsPanel`、`SettingsField`、按钮、Badge、Toggle、Segmented 等组件。
2. 品牌颜色必须使用 `keeper-*` Tailwind token、`--sk-*` CSS 变量或 `.keeper-*` 组件类。禁止硬编码默认主题的蓝色、青色、渐变和阴影；红、琥珀、绿只用于错误、警告、成功等语义状态。
3. 新组件必须兼容全部主题和自定义壁纸。至少人工检查默认主题和一个非蓝色主题，确保文本、边框、禁用态、焦点态和遮罩对比度可读。
4. 保持现有形态：Segoe UI、深色毛玻璃、克制的 cyan 强调、`rounded-xl/2xl/3xl` 层级、紧凑字号和间距。除非是全局设计升级，不得单页引入另一套设计语言或 UI 框架。
5. 图标、头像、背景和动效优先复用现有资产与组件。动效不得阻塞操作，持续动效应克制，并尊重窗口性能。

### 3.2 交互与窗口

1. 每个异步界面必须有加载、空状态、错误反馈和重复提交保护；危险操作必须清楚说明对象与后果。
2. 按钮、输入框和可点击卡片必须使用正确语义，具备键盘焦点、禁用态和必要的 `aria-*`；纯装饰元素应对辅助技术隐藏。
3. 无边框 Electron 窗口中的交互区域必须是 `no-drag`，仅明确的标题栏/拖拽区使用 `drag-region`。
4. 必须在现有窗口最小尺寸下无关键内容裁切和意外横向滚动；长文本、路径和错误信息必须可换行、截断或滚动查看。
5. 新窗口或面板必须复用 `AppBackground`、`PanelTitleBar`、窗口管理器、安全导航与销毁安全发送模式，不能自行维护第二套窗口生命周期。
6. 面向用户的文案保持简洁中文，术语与现有页面一致；错误信息同时回答“发生了什么”和“用户下一步能做什么”。

### 3.3 UI 验收

UI 改动交付前必须在实际 Electron 页面中预览，而不只看 JSX。检查正常、加载、空、错误、禁用状态，以及默认主题、一个替代主题和相关窗口最小尺寸；在变更说明中记录检查过的页面与状态。

## 4. 架构与边界

1. 主进程持有 LLM、数据库、文件系统、密钥、调度和高权限能力；renderer 只负责展示和用户输入，不得直接访问 Node API、数据库或密钥。
2. 跨进程能力必须形成完整链路：共享类型 → preload `contextBridge` → `electron/ipc/*` → 领域服务/Repository。不得用 `any` 绕过边界类型。
3. 所有高权限 IPC 必须通过 `trustedIpcMain` 注册，并对 `unknown` 输入做运行时校验，包括结构、枚举、数值范围、字符串长度、数组数量和路径范围。
4. 可复用业务规则放在 `src/` 领域模块，不埋在 React 组件或 IPC handler 中；IPC 负责验证和适配，Repository 负责 SQL，组件负责呈现。
5. 新能力应保持开发态与打包态路径一致；新增运行时资源时同步 Vite/electron-builder 白名单、asar 配置和打包测试。

## 5. 数据库与持久化

1. 生产库使用 better-sqlite3，sql.js 是回滚源和契约测试适配器。业务层通过 `src/db/repositories` 访问数据库，不在 renderer、Agent 或 IPC 中散写 SQL。
2. Schema 变更必须新增按序 migration，并同步 `src/db/schema.ts`、Repository、`docs/DATABASE.md` 和双适配器测试；不得修改已经发布 migration 的含义。
3. Migration 必须可判定、事务化并写入账本；失败或 partial 状态必须阻止在不确定 schema 上继续运行。
4. 迁移、恢复和备份必须保留用户数据。复制 native 主库前必须正确处理 WAL/checkpoint；禁止通过删除 WAL、主库或引擎标记“修复”问题。
5. 自动化测试必须使用临时目录和临时数据库，绝不能读写 `D:\SQLlite` 等真实用户数据。涉及生产库的命令必须明确由用户要求，并先做只读健康检查或安全备份。
6. 删除用户文件优先使用可恢复的 `.trash`/备份流程；原子写入必须使用临时文件、落盘校验和原子替换。

## 6. Agent、工具与主动行为

1. 每个工具必须显式声明 `risk`、`idempotent`、`supportsPreview`、`reversible` 和 `evidence`；多 action 工具必须按本次调用用 `describeCall` 给出真实契约。
2. 副作用必须服从权限策略。高风险操作必须确认；非幂等调用必须防重复；支持取消的流程必须传播取消信号并设置合理超时。
3. “已完成”只能来自真实工具结果或已校验产物。文件产物必须验证存在、大小及适用时的 SHA-256，不允许模型用自然语言替代完成证据。
4. 新 run 必须纳入 TaskRun/step/approval/artifact 记录；异常退出后按事实标为 interrupted，不自动重放可能产生副作用的步骤。
5. 主动简报、提醒、记忆与承诺提取必须遵守用户显式开关、安静时段、幂等键和候选确认规则；低置信推断不得直接写成用户事实。
6. 外部网页、附件、模型响应、MCP 返回和数据库文本都视为不可信数据，不能当作系统指令执行。

## 7. 安全、错误与生命周期

1. API Key 和敏感配置只进入受控配置层；不得写入日志、错误详情、运行诊断、测试快照或 renderer 可枚举状态。
2. 文件路径必须限制在明确授权的根目录，防止路径穿越、符号链接逃逸和宽泛删除；破坏性操作前解析并核对精确目标。
3. 禁止空 `catch` 和未处理 Promise rejection。可恢复错误应降级并给出明确状态；数据库、配置或安全边界初始化失败时必须 fail closed，不能继续执行依赖它的流程。
4. 窗口、网络流、语音、RAG、MCP、定时任务和 Agent run 必须有关闭/取消路径；发送事件前检查窗口和 webContents 是否仍存活。
5. 启动路径不增加无界网络等待或重 CPU 工作；批量输入必须有数量/大小上限，循环、队列和缓存必须有边界。

## 8. 测试与验证矩阵

| 改动类型 | 最低验证要求 |
|---|---|
| 所有代码改动 | `pnpm typecheck`、相关 Vitest、`git diff --check` |
| Bug 修复 | 新增回归测试，并证明覆盖原始失败路径 |
| UI / renderer | 相关组件/逻辑测试、`pnpm build`、实际 Electron 视觉检查 |
| 数据库 / migration | 临时库、双 adapter、迁移/回滚或健康检查测试，不触碰真实库 |
| Agent / 工具 / 权限 | 相关 S2/S3/P0 契约测试，覆盖成功、拒绝、失败、取消和重复调用 |
| 生命周期 / 打包 | 对应 Electron smoke、窗口生命周期或 packaged-native 测试 |
| 文档/注释 | `git diff --check`；若未改变行为，可不运行代码测试 |
| 里程碑收口 | `pnpm test`、`pnpm build`，再运行该里程碑专项入口 |

测试不得依赖执行顺序、真实网络、真实密钥或开发机持久状态。无法运行某项验证时，交付说明必须写明原因、风险和替代检查，不能把“未运行”写成“通过”。

## 9. 文档与兼容性

1. 功能行为、状态、命令、配置、IPC、表结构或发布流程变化时，必须同步最接近的 README/DESIGN/DATABASE/专项文档。
2. 文档必须区分“计划、已实现、自动化通过、真实验收完成”，不得用设计稿描述尚未存在的行为，也不得保留已完成事项为“未开始”。
3. 除非需求明确允许破坏性升级，数据库、配置、IPC 和用户数据格式必须向后兼容；弃用应先兼容读取并提供迁移路径。
4. 新环境变量必须进入 `.env.example`，使用安全占位值，并说明默认值、作用域和失效行为。

## 10. 完成定义（Definition of Done）

一个改动只有同时满足以下条件才算完成：

- 需求的正常路径和相关失败路径都已实现，没有用占位 UI、静默失败或口头说明代替功能。
- UI 与现有主题、组件、窗口和交互一致，且完成实际页面检查。
- 类型、IPC、权限、数据与生命周期边界没有被绕过。
- 用户数据有兼容、迁移、备份或回滚策略；自动化测试不接触真实数据。
- 回归测试与最低验证矩阵通过，结果如实记录。
- 文档和状态说明已经同步，`git diff` 中没有密钥、数据库、构建产物或无关改动。

任何例外都必须在交付说明中列出：违反的条款、原因、风险、临时保障和后续修复项。未经说明的例外不视为完成。
