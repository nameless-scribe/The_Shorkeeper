## 1. 目标与边界

**要解决的**：把一段本地录音变成可检索、可追溯、可执行的东西——逐字稿进工作区，纪要里的待办进 P0，而不是给用户丢一坨文本。

**同时解决的**：聊天框至今不能语音输入（`useVoiceInput` 只接在语音通话页），而配置里 `pushToTalk` / `sttAutoSend` 两个设置项早就定义好却从未被任何代码读取。

**不解决的**：见第 7 节。

## 2. 供应商选型（2026-09-13）

### 2.1 结论：腾讯云「录音文件识别极速版」

| 项 | 结论 |
|---|---|
| 传文件 | **HTTP body 直接放二进制**（`Content-Type: application/octet-stream`），不需要对象存储，也不必 base64（省掉 4/3 膨胀） |
| 上限 | **100 MB / 2 小时** |
| 调用模型 | **同步**：一次 POST 直接拿结果，30 分钟音频约 10 秒完成 |
| 说话人分离 | `speaker_diarization`（0/1），中文普通话引擎支持 |
| 时间戳 | `sentence_list` 内含句子级 `start_time` / `end_time` |
| 格式 | wav、pcm、ogg-opus、speex、**silk**、mp3、m4a、aac、**amr** |
| 鉴权 | **TC3-HMAC-SHA256 签名**（SecretId + SecretKey），不是 Bearer token |
| 免费额度 | **每月 5 小时**，月度重置 |
| 超出单价 | 3.10 元/小时（0–299 小时档）；预付费 30 小时 72 元（2.4 元/小时） |

**同步返回是选它的核心理由**。它让本计划整体少掉一大块：不需要任务 id、不需要退避轮询、
不需要跨重启恢复、不需要处理结果地址的有效期。这些复杂度全部只为异步接口存在。

格式覆盖也是最广的一家：`silk` 是微信语音，`amr` 是老式录音，标准版还支持 mp4（会议录屏）。

**成本量级**：按每月 10 小时会议估算，5 小时免费 + 5 小时 × 3.10 ≈ **15.5 元/月**。
个人规模下金额可忽略，因此 P4.2 的"提交前显示费用预估"降级为**只显示音频时长**，
不做金额换算——金额换算要跟踪价格变动，收益远小于维护成本。

### 2.2 为什么不是阿里百炼（尽管它便宜 10 倍）

`paraformer-v2` 单价 0.288 元/小时，是所有选项里最便宜的，**但它和所有百炼文件转写模型
一样只收公网 URL**。API 文档原文："不支持 Base64 编码方式的音频"、"仅支持可通过公网访问的
URL 所指向的音频的识别，不支持识别二进制流，也不支持直接识别本地文件"。逐个核实过
`paraformer-v2`、`fun-asr`、`qwen-audio-3.0-asr-flash-filetrans`，结论一致。

这意味着走百炼就必须接 OSS：多一套凭证、多一个存储桶生命周期要管，音频还要先落到一个
存储服务而不只是发给模型。每月省下的十几块钱不值得换这些。

> **记录一次判断失误**：本文最初版本断言"百炼支持 `data:<mediatype>;base64,<data>` 内联，
> 因此不需要 OSS"，并把这一条写成"本计划成立的前提"。该结论来自对多模型文档页的误读——
> 支持 base64 的是**同步的 `qwen3-asr-flash`**（≤5 分钟 / 10 MB，且不支持说话人分离），
> 而不是任何文件转写模型。教训：**跨模型的能力描述必须落到具体模型的 API 参考页去核**，
> 汇总页和选型页会把不同模型的能力混在一起讲。

### 2.3 其他候选

| 候选 | 结论 |
|---|---|
| **讯飞语音转写** | 支持分片上传、不碰对象存储，角色分离可指定人数，中文能力强。但价格最高（9.9 元/小时起，按每月 10 小时约 99 元），且需分片 + 异步轮询，复杂度接近百炼方案。**不采用** |
| **腾讯云录音文件识别（标准版）** | 免费额度更多（每月 10 小时）、单价更低（1.75 元/小时），但 base64 直传**限 5 MB**（约 5–10 分钟），长音频仍需 COS URL。免费额度再多也用不上。**不采用** |
| **DeepSeek** | API 只接受文本输入，无原生 ASR。社区方案一律外挂第三方 STT。**不具备该能力** |
| **本地部署** | 见第 7 节，因目标设备条件已关闭 |

### 2.4 供应商与对话模型必须解耦

对话模型走百炼（或用户日后换成别家），转写走腾讯云——**这是两套独立凭证、两个不同的
鉴权方式**。配置层必须体现这一点，不能把转写凭证挂在 `modelConfig` 上，见 4.3。

### 2.5 待真实调用复核的三件事

文档不足以定论，**P4.2 第一次真实调用必须同时验证**：

1. **说话人分离支持几人**。极速版文档未标注人数上限；但标准版明确写的是"单通道**双人**对话"。
   两个是不同接口，需用三人以上的真实录音实测。
2. **真实响应的 JSON 结构**。`sentence_list` 的确切字段名与嵌套层级需要核对后再收紧映射。
3. **极速版的签名方式**。腾讯云部分接口用的不是标准 TC3-HMAC-SHA256；且极速版请求体是
   二进制，签名时对 body 取哈希的方式要拿官方示例核对。

## 3. 为什么不能只做成一个技能

技能是**编排层**：`SKILL.md` 的 frontmatter 声明 `allowedTools`，本质是告诉模型
"按这个流程调这些已注册的工具"。它不能新增能力。

当前没有任何工具能把音频变成文字，技能就没有东西可编排。因此必须分三层，自下而上：

| 层 | 产出 | 没有它会怎样 |
|---|---|---|
| L1 能力 | `src/voice/tencent-file-asr.ts` + `tencent-signature.ts`：签名、上传、解析 | 无 |
| — | L1 对上暴露统一接口，**不把供应商概念漏到工具层**（签名、`sentence_list`、引擎类型等一律封在 L1 内）。这条已经兑现过一次价值：供应商从百炼改为腾讯云时，`asr-contract.ts` 与 `transcript-format.ts` 一行未动，见 10.2 | 换供应商会波及整个上层 |
| L2 工具 | `transcribe_audio`：声明副作用、风险、幂等与完成证据，逐字稿落工作区 | 模型无法调用 |
| L3 技能 | `meeting-notes`：转写 → 读稿 → 出纪要 → 确认后写入 P0 | 每次都要用户手工串流程 |

技能是最后也最省事的一层，但只有它能把"会议纪要"变成产品而不是一个转写器。

### 3.1 转写与总结必须是两步

**不要**做成一个"上传录音直接给纪要"的工具。理由：

- 转写慢且按时长计费；总结便宜且经常要重来（"再详细点"、"按项目分组"、"补上时间线"）
- 合成一步意味着每次调整纪要格式都要重新转写一次
- 逐字稿本身有独立价值（可检索、可引用、可回溯"他到底怎么说的"）

所以：`transcribe_audio` 只产出逐字稿文件并返回路径；纪要由模型读这份文件生成。

### 3.2 逐字稿不能直接进上下文

一小时会议的逐字稿轻松上万字。工具返回**产物路径 + 摘要元信息**（时长、说话人数、
分段数、前 200 字预览），模型按需用现有文件工具读取片段。这与 P1 "不复制正文"、
RAG `catalog` 模式的既有取舍一致。

## 4. 数据与契约

### 4.1 新增持久化

新增 migration `0027_audio_transcripts.sql`，一张表：

| 列 | 说明 |
|---|---|
| `id` | uuid |
| `source_path` | 工作区相对路径（音频） |
| `source_hash` | 音频内容 SHA-256，**幂等键**：同一文件不重复转写 |
| `duration_ms` / `size_bytes` / `channels` | 音频元信息 |
| `provider` / `engine` | 供应商标识与引擎类型（如普通话 16k），便于日后换供应商时区分历史记录 |
| `status` | `running` / `succeeded` / `failed` / `cancelled` |
| `transcript_path` | 逐字稿产物的工作区相对路径，可空 |
| `speaker_count` | 分离出的说话人数，可空 |
| `error` | 失败原因，限长脱敏 |
| `sensitivity` | 默认 `sensitive`，见 4.4 |
| `created_at` / `updated_at` / `completed_at` | |

**不存逐字稿正文**，只存路径。理由同 P1：账本不复制正文。

`source_hash` 作幂等键意味着：同一个录音重复拖进来，直接返回已有逐字稿，不重复计费。

**没有 `provider_task_id`，也没有 `pending` 状态**：极速版同步返回，请求发出即在等结果，
不存在"已提交但尚未开始"的中间态。

### 4.2 失败与中断

同步调用把跨重启恢复这个问题整体消掉了：进程退出即请求中断，没有遗留在服务端的任务需要接回。
需要处理的只剩两类：

- **请求失败或超时**：记 `failed` 与原因，用户可重试。因为有 `source_hash` 幂等，
  重试成功后不会产生两份逐字稿。
- **进程中途退出**：启动时把仍是 `running` 的记录改判为 `failed`（原因"应用退出"），
  不留下永远不会推进的僵尸记录。

一次调用要传最多 100 MB 并等待数十秒，因此**必须支持取消**，且取消要真正中止 HTTP 请求
（`AbortSignal` 贯穿到底），不能只是界面上装作停了而后台仍在传。

### 4.3 供应商配置与对话模型解耦

转写走腾讯云，对话走百炼——**两套凭证、两种鉴权方式**，必须分开存。

- `src/config/voice.ts` 新增一组独立配置：`asrProvider`、`asrSecretId`、`asrSecretKey`、
  `asrRegion`、`asrEngineType`。解析顺序沿用现有 TTS 端点那套：应用内设置 → `.env` → 默认。
- **不要复用 `resolveVoiceApiKey()`**：它返回单个字符串，装不下一对凭证，
  而且它的回落链会拿到百炼的 key，用在腾讯云上只会得到一个难懂的鉴权错误。
- **不得把 ASR 凭证绑到 `modelConfig`**。用户换对话模型时，转写不应受影响。
- `SecretKey` 是长期凭证，权限范围取决于账号类型。设置页需明确提示**使用子账号密钥、
  只授予语音识别权限**，并与现有 API Key 一样做掩码显示、不回显明文。

### 4.4 敏感性默认从严

会议录音比聊天文本敏感得多：可能含他人声音、未公开的商业信息。

- 转写记录默认 `sensitivity = 'sensitive'`
- 逐字稿**不自动进 RAG 知识库**，需用户显式归档
- 沿用 P1 已有的 `model_use_policy` 概念：标记为 `deny` 的转写稿不送远端 embedding
- 音频本身**不上传到任何对象存储**——这正是放弃更便宜的百炼方案、选腾讯极速版的理由之一：
  音频只在一次 HTTPS 请求里发给识别服务，不会在任何存储桶里留存
- 设置页明确告知：转写会把音频发送给语音识别服务商（与对话模型不是同一家）

### 4.5 附件类型必须分类

现在的附件语义是"读进来给模型看"。音频不能这样处理，否则模型会试图把 mp3 当文本读。

- `WORKSPACE_IMPORT_EXTENSIONS` 扩展出独立的 `WORKSPACE_AUDIO_EXTENSIONS`。按供应商实际支持的清单取：
  `.mp3` / `.wav` / `.m4a` / `.aac` / `.flac` / `.ogg` / `.opus` / `.amr` / `.silk`
  （后两个分别是老式录音与微信语音，正是"手上已有的录音"最常见的两种）
- `WorkspaceAttachment` 增加 `kind: 'text' | 'office' | 'audio'`
- 上下文构建遇到 `audio` 附件时，注入的是"这是一个待转写的音频文件，路径 X"，而不是文件内容
- 音频不受 `MAX_WORKSPACE_IMPORT_BYTES = 20MB` 约束，**上限取 100 MB**，与极速版硬上限一致——
  设得比供应商上限高只会让用户在上传成功后才收到失败

## 5. 实施阶段

实际为五个阶段：P4.0、P4.1、P4.2、P4.4、P4.5。**P4.3 已并入 P4.2，编号留空。**

### P4.0 — 契约、端点与固定样本（2–3 天）

**状态：已完成。** 实施记录见 10.2。

- 固定转写结果的内部表示：句子数组（`beginMs` / `endMs` / `text` / `speakerId?`），
  与供应商返回结构之间的映射写成纯函数并测试。
  （本阶段完成时供应商还是百炼，随后变更为腾讯云；受影响的两个模块在 P4.2 重写，见 10.2。）
- 固定逐字稿的 Markdown 产出格式：带时间戳与说话人标签，同一说话人连续发言合并。
- 端点推导、模型名、语言提示、分离开关的解析规则，含缺配置时的清晰报错。
- 固定样本：单声道双人对话、无人声静音段、超长静默、单句极短音频、非法容器、
  供应商返回 FAILED、轮询超时、同一文件重复提交。
- 建立 `pnpm test:p4`。

**阶段出口**：映射与格式化有确定输出；不改变任何生产行为；不发出任何真实网络请求。

### P4.1 — 聊天框语音输入（2–3 天）

**状态：已落地，待真机验证。** 实施记录见第 10 节。

与转写文件解耦，可独立发布。所有零件已存在，只是没接线。

- `useVoiceInput` 接入 `InputBar`，加麦克风按钮与录音中的电平反馈。
- 激活两个休眠设置：`pushToTalk`（按住说话 vs 点击切换）、`sttAutoSend`（识别完是否自动发送）。
- 设置页 → 语音，补上这两项的 UI。
- 识别结果回填输入框，**默认不自动发送**，用户可改。识别失败保留已输入文本，不清空。
- 录音中禁用发送按钮；切换会话或窗口失焦时安全终止录音。

**阶段出口**：真机上按住说话能把识别文本填进输入框；`pushToTalk` 与 `sttAutoSend`
两种组合均符合预期；录音期间崩溃或切窗不残留麦克风占用。

### P4.2 — 音频转写全链路（5–7 天）

> 原 P4.2（短音频同步）与 P4.3（长音频异步）已合并为一条同步通道。
> **P4.3 编号留空不再使用**，沿用 P2 取消时的处理方式：不整体改号，
> 以免历史讨论、测试入口与文档交叉引用全部失效。

只有一条路径：签名 → POST 二进制 → 同步拿结果。短音频与两小时会议走的是同一条路。

**开工顺序是先验证、后建设**，因为 2.5 那三件事会影响后面所有实现：

1. **第一步：签名 + 一次最小真实调用**。拿一段三人以上的真实录音，同时确认连通性、
   说话人分离实际支持几人、真实响应的 JSON 结构。这一步的产出是一份真实响应样例，
   之后据它收紧映射。
2. `src/voice/tencent-signature.ts`：TC3-HMAC-SHA256 签名，纯函数，用官方测试向量固定。
   不引入 `tencentcloud-sdk-nodejs`——签名约 80 行，引 SDK 会增加打包体积并与
   `AGENTS.md`"不引入平行体系"相悖。
3. `src/voice/tencent-file-asr.ts`：**供应商概念一律封在本模块内**，
   对上只暴露"给一个音频路径，拿回句子数组"。`AbortSignal` 贯穿到底，取消要真中止请求。
4. 重写 P4.0 留下的两个供应商相关模块：`asr-mapping.ts` 换成腾讯响应结构，
   `asr-endpoint.ts` 换成腾讯端点（并因去掉轮询而大幅简化）。
   `asr-contract.ts` 与 `transcript-format.ts` **不动**——它们本就与供应商无关。
5. migration `0027` 与 Repository；`source_hash` 幂等，重复提交同一文件不重复计费。
6. 说话人分离：`speaker_diarization`，按第 1 步实测结论决定人数上限与降级策略。
7. 启动时把残留的 `running` 记录改判 `failed`（原因"应用退出"），不留僵尸记录。
8. 进度可见：运行记录页能看到"转写中 / 已完成 / 失败"，复用 P0 `TaskRun` 的展示。
9. 工具 `transcribe_audio`：声明有副作用（写文件、产生费用）、以 `source_hash` 去重、
   可取消、完成证据为逐字稿文件的 SHA-256。提交前**只显示音频时长，不做金额换算**（见 2.1）。
10. 附件分类（4.5），拖拽 mp3 进聊天框不再被当文本读。

**阶段出口**：一场真实会议录音（2 小时以内）能完整转写并带说话人标签；
短录音走同一条路径也能跑通；重复拖同一文件不重复计费；转写中途取消能真正中止请求；
应用中途退出后不留下卡在"转写中"的记录；失败时用户看到可理解的原因而不是原始报错；
工具在权限确认、取消、失败三条路径上均符合 S3 工具契约。

### P4.4 — 会议纪要技能与 P0 衔接（3–4 天）

- `skills/meeting-notes/SKILL.md`，`trigger: auto`，`matchKeywords` 含"会议纪要 / 整理录音 / 总结这段录音"等。
- 流程：定位音频 → `transcribe_audio` → 读逐字稿 → 产出纪要（议题 / 结论 / 待办 / 负责人 / 截止）
  → **向用户确认** → 确认后调 `create_user_task` 与 `manage_commitments` 落库。
- 纪要中每条待办必须能回指逐字稿的时间戳，做到可追溯。
- 不确认不写入；不自动给他人创建承诺（`promisedTo` 只记录，不代他人承诺）。

**阶段出口**：一段真实会议录音能走完"转写 → 纪要 → 确认 → 待办入库"；
生成的承诺随后能被 P3 的承诺守望正常跟进；用户拒绝确认时不产生任何领域数据。

## 7. 明确不做

- **不接对象存储（OSS / COS）或任何云盘**。音频只在一次 HTTPS 请求里发给识别服务，
  不在任何存储桶里留存。这条约束直接决定了供应商选择：它排除了单价最低的百炼方案（见 2.2）。
- 不做实时会议转录（边开会边转写）——那是另一套实时流式链路，本计划只处理已有的录音文件。
- 不做声纹识别（认出"这是张三"）；说话人分离只给匿名 `speaker_id`。
- 不自动把逐字稿灌进 RAG 知识库。
- 不在用户确认前创建任何待办、承诺或日程。
- 不为转写单独建一套运行记录 / 通知体系，复用 P0 `TaskRun` 与 P3 事件账本。
- 不支持 DeepSeek 等不提供 ASR 的供应商做转写；对话模型与转写供应商解耦。
- **不做本地转写**（whisper.cpp / sherpa-onnx / Vosk）。评估过：项目已依赖 `onnxruntime-web`
  与 `@ricky0123/vad-web`（语音通话 VAD），本地推理的运行时与资产分发地基其实已经具备，
  且本地方案能让 4.4 的隐私顾虑整体消失、无按时长计费。**但目标设备不具备本地部署条件**，
  该方向就此关闭，不再重复评估。若日后设备条件改变，需要重新权衡的是：模型体积（几百 MB 起，
  与现有精简打包白名单冲突，须改为首次使用时下载）、CPU 转写耗时（一小时会议约十几到几十分钟）、
  中文精度（本地小模型大概率不及针对中文调优的 Paraformer / Qwen3-ASR）、
  以及最大的短板——说话人分离在本地需额外接声纹嵌入与聚类，工作量超过转写本身。

## 8. 推荐开工顺序与停线条件

建议顺序：**P4.1（已完成）→ P4.0 → P4.2 → P4.4 → P4.5**。

把 P4.1（聊天框语音输入）提到最前，理由：它与转写完全解耦、零件全部现成、半天到两天可见效果，
而且顺手激活两个躺了很久的死配置。先拿到一个能用的东西，再啃转写。

P4.0 紧随其后：它不发任何真实网络请求、不改生产行为，却能在不花钱、不碰真实 API 的前提下
把 P4.2 的接口形状定死。等真正接 API 时只剩"发请求"一件事。

出现以下任一情况立即停止扩大范围：

- 同一音频重复转写产生重复计费；
- 逐字稿正文进入数据库或被整段注入模型上下文；
- 音频附件被当作文本读取；
- 取消转写后 HTTP 请求仍在后台继续传输；
- 应用退出后留下永远停在"转写中"的记录；
- 为了绕开 100 MB / 2 小时上限而引入对象存储；
- 转写凭证与对话模型凭证互相串用；
- 未经用户确认就写入待办、承诺或修改任何领域真源；
- 转写失败后用户只看到供应商原始报错；
- 为了赶长音频而在 `InputBar` 里引入新的带副作用 state updater（见 P3 §9.6 的教训）。

## 10. 实施记录

### 10.1 P4.1 聊天框语音输入（2026-09-13）

开工前核对发现：`pushToTalk` 与 `sttAutoSend` 的**持久化与 IPC 校验早已完整**
（`electron/ipc/voice.ts` 的 `parseVoiceSettingsPatch` 已按布尔值校验，`src/config/voice.ts` 已读写），
缺的只有 UI 与接线，因此实际工作量小于计划估算。同时发现设置页连 `sttEnabled` 的开关都没有
（默认 `true` 但无处关闭），一并补上。

| 层 | 文件 | 说明 |
|---|---|---|
| 纯逻辑 | `src/renderer/components/voice-input-controls.ts` | 按钮状态推导、识别结果并入草稿、是否自动发送、电平夹紧；9 个用例 |
| 输入框 | `src/renderer/components/InputBar.tsx` | 麦克风按钮与电平条；正文改由 `applyText` 统一写入 |
| 聊天页 | `src/renderer/ChatPage.tsx` | 复用已有的 `refreshVoiceSettings` 递增 nonce 通知输入栏重读设置，不新增调用点 |
| 设置页 | `src/renderer/settings/VoicePage.tsx` | 新增"语音输入（聊天框）"一节：启用开关、按住说话 / 点击切换、识别后自动发送 |

几个不显然的取舍：

- **录音中按钮必须保持可点**，即使输入框因模型开始运行而被禁用——否则麦克风会一直占着。
- **识别为空时一律不发送**，也不清空草稿；否则会发出空消息或误发此前的草稿。
- 按住说话与点击切换**分开接线**（`onPointerDown/Up/Leave` 对 `onClick`），不混用以免双触发；
  指针移出按钮即取消录音。
- **失焦与页面隐藏时取消录音**。`InputBar` 与应用同生命周期、不会卸载，
  `useVoiceInput` 的卸载清理在正常使用中不会触发，录音的结束完全依赖显式调用。
  时长兜底沿用 `record-pcm.ts` 已有的 5 分钟硬上限（到点 `teardown()` 释放设备并报错），
  **不新增第二个计时器**。
- 切换会话不中断录音：输入框正文本来就跨会话保留，语音输入与手打文本行为保持一致。

验收：`pnpm typecheck`、全量 775 用例、`pnpm test:ui:strict` 三个冒烟（`rendererConsoleClean`）、
`pnpm build` 均通过。

**仍需真机验证**（自动化只覆盖纯逻辑，麦克风链路测不到）：按住说话与点击两种模式、
自动发送、不覆盖已输入内容、空录音、指针移出取消、改完设置关闭抽屉后即时生效。

### 10.2 P4.0 契约、端点与固定样本（2026-09-13）

四个纯模块，全部不依赖 Electron、数据库与网络：

| 文件 | 职责 |
|---|---|
| `src/voice/asr-contract.ts` | 内部表示（`TranscriptSentence` / `TranscriptResult` / `AsrTaskStatus`）、固定常量、提交前校验、幂等键 |
| `src/voice/asr-mapping.ts` | 供应商返回 → 内部表示；防御性解析，缺字段一律降级不抛错 |
| `src/voice/transcript-format.ts` | 内部表示 → 逐字稿 Markdown；连续发言合并、说话人编号、静默标注 |
| `src/voice/asr-endpoint.ts` | 端点推导、提交 / 轮询 URL 构造、退避节奏、base64 data URI |

几个定下来的规则：

- **未知任务状态按失败处理**，不按"还在跑"。否则供应商返回 `CANCELED` 之类的值会导致无限轮询。
- **成功但没有结果地址判为失败**。没有结果的"成功"对调用方毫无意义，放行只会在读取阶段炸得更难定位。
- **声道未知时不开启说话人分离**。拿到一份不可用的分离结果比没有分离更糟。
- **幂等键含模型与是否分离**（`asr:{hash}:{model}:{diar|plain}`）。同一文件在不同设置下结果不同，
  否则用户打开分离后拿到的还是旧的无分离结果。
- **逐字稿用两级阈值**：间隔超过 10 秒断开段落，超过 60 秒才额外标注静默——
  前者防止整篇挤成一段，后者避免频繁打断阅读。
- **说话人按首次出现顺序编号**，"说话人 1"始终是最先开口的那位，与供应商的匿名 id 无关。
- **正文做 Markdown 转义**：逐字稿可能以 `#` `-` `>` 开头，原样写入会被渲染成标题或列表。
- 自设 100 MB 上限。当时的理由是"base64 内联把请求体放大 4/3，不能贴着百炼的 2 GB 上限走"；
  换到腾讯极速版后该理由作废，但 **100 MB 恰好就是极速版的硬上限**，数值不必改，
  只需把 `asr-contract.ts` 里的注释与常量名改成对应新的依据。

其中前两条（任务状态、结果地址）与轮询相关，**换到同步接口后不再适用**，P4.2 重写映射时移除。

自建入口 `pnpm test:p4`：8 个文件 80 个用例（含 P4.1 与既有 STT / 端点测试）。
固定样本覆盖：单声道双人对话、全静音、单句极短音频、空白句与字符串时间戳、
时间倒挂、多声道乱序合并、非法容器、超限体积、供应商 FAILED、成功但无结果地址、
轮询退避与放弃、畸形响应。

**阶段出口已满足**：`pnpm typecheck`、全量 828 用例、`pnpm build` 通过；
四个新模块**未被任何生产代码引用**（已用 grep 确认），**不含任何 fetch / WebSocket**。

**供应商变更后的影响（2026-09-13 当日）**：P4.0 完成后不久，因发现百炼文件转写不支持
本地直传而改选腾讯云极速版（见 2.2）。这次变更验证了 P4.0 的分层是对的：

| 模块 | 是否受影响 |
|---|---|
| `asr-contract.ts` | **不受影响**。内部表示、校验、幂等键本就与供应商无关 |
| `transcript-format.ts` | **不受影响** |
| `asr-mapping.ts` | 需按腾讯 `sentence_list` / `start_time` 结构重写 |
| `asr-endpoint.ts` | 需换成腾讯端点，并因取消轮询而大幅简化 |

四个模块有两个原样保留，而这两个恰好是逻辑最密的部分（格式化 + 校验 + 幂等）。
若当初没有把供应商概念隔离在 L1，这次变更会波及整个上层。

后两个模块的重写放在 P4.2，不在 P4.0 回头改——它们要对着真实响应写，
而真实响应要等第一次真实调用才有。原先记录的"结果 JSON 多形态兼容"问题一并作废，
新的映射直接按实测结构写，不再预设兼容分支。

### 10.3 P4.2 第一步：极速版请求签名（2026-09-13）

先实现了标准云 API 的 TC3-HMAC-SHA256，随后发现**极速版根本不走标准云 API 规范**，
该实现对本接口无效，已撤除。正确的形态是：

| 项 | 极速版 | 标准云 API（不适用） |
|---|---|---|
| 域名 | `asr.cloud.tencent.com` | `asr.tencentcloudapi.com` |
| AppID | 在**路径**里 `/asr/flash/v1/{appid}` | 不需要 |
| 业务参数 | **query string** | JSON body |
| 请求体 | 纯音频二进制 | JSON |
| 签名 | **HMAC-SHA1 + base64** | TC3-HMAC-SHA256 |
| 签名位置 | `Authorization` 头 | `Authorization` 头 |

签名原文 = `POST` + host + path + `?` + 按键名字典序排列的 `k=v`（`&` 连接），
**不含协议头、不做 URL 编码**。

**这是本轮第二次同类失误**：第一次是把百炼多模型汇总页的 base64 能力套到文件转写模型上（见 2.2），
这次是从"搜索结果里出现过 TC3"推断它适用于极速版。共同点都是**拿通用/汇总文档的结论套到具体接口上**。
此后新增一条自查：**接入任何接口前，必须在该接口自己的 API 参考页确认域名、鉴权方式与参数位置**，
不接受来自产品总览页或他处的间接结论。

测试向量的取舍：腾讯云文档里的密钥同样是打码的，最终签名不可复现。但 HMAC-SHA1 是公开标准，
因此用 **RFC 2202 的标准测试向量**验证签名原语——这能把"算法选错"（例如误用 SHA256）
挡在真实调用之前，比自己造一个金值有意义得多。其余锁的是拼接规则：
参数排序、空值丢弃、原文不带 `https://`、签名原文与实际 URL 逐字对应、AppID 在路径不在 query。

**仍需真实调用确认**：最终签名能否通过服务端校验，以及 2.5 列的另外两件事。
