# ERP 对话报工约定

状态：**输入规范、源码适配、浏览器/草稿/审批/提交/回查代码与模拟测试已完成首轮；真实账号登录、验证码样本和真实报工仍未验收。**

本文件记录 2026-09-20 用户提供的规则与源码适配事实，包括后续明确的自由表达偏好。已实现边界以实施计划中的进度记录为准；模拟闭环通过不等于真实 ERP 已验收，只有工具回查到真实新增记录后才能声称某次报工完成。

技术选型、模块拆分、阶段任务和验收门槛见 [ERP 对话报工实施计划](./ERP-WORK-REPORT-IMPLEMENTATION-PLAN.md)。

## 当前使用与恢复

1. 在“设置 → ERP 报工”启用功能，填写站点、浏览器和账号；密码只在本机配置。连接专用浏览器后完成登录，自动验证码登录失败时可在保留的窗口中人工接管。
2. 在聊天中自然描述日期、任务、工作内容和工时，先让守岸人整理草稿；不明确的任务或时长需要补充。说“改成四小时”等更正会修订草稿，不会直接写 ERP。
3. 明确要求提交后，核对确认弹窗中的账号、日期、任务、内容、当天已报与提交后合计。只有点击“确认并执行”才开始逐条新增；每条都要回查到唯一远端记录才标为已核验。
4. 结果未知时使用批次 ID 请求回查。回查没有唯一证据时继续停下人工核对，不重复提交。部分条目已核验且没有结果未知时，可以明确要求接续该批次；接续只预览剩余条目，并要求一次新的确认。
5. 在“设置 → 运行记录”打开对应运行，可查看冻结的报工内容、批次当前状态、逐条核验状态，以及该次运行是否尝试过该条。跨运行接续后，历史运行显示的是批次**当前**状态。

当前只完成模拟环境验证，其中新打包程序已通过本地浏览器表单的取消与一次确认写入探针。真实 ERP 登录、验证码样本、实际写入，以及打包应用内审批到回查的完整流程仍需验收；不能把模拟测试视为真实报工成功。

## 1. 已确认需求

- 用户在守岸人对话中描述工作，由守岸人整理并通过浏览器完成 ERP 报工。
- 用户不需要遵循固定输入格式；支持自然语言、分条描述和同一对话中的补充、更正。统一结构由守岸人整理为待确认草稿。
- 同一用户、同一报工日期的工时合计最多 **8 小时**，包括 ERP 中已有记录与本批新增记录，跨所有任务统计。
- 允许 **0.5 小时**等小数工时。用户没有要求只能填写半小时的整数倍。
- 日期通常为当天；在草稿中展开为明确日期，提交前再核对，不能在跨午夜后静默换日。
- ERP 源码由用户提供，位于 `D:\erp`；当前只读核查，不修改 ERP、不读取真实数据库。

## 2. 自由表达，统一整理成草稿

用户可以像平时聊天一样描述今天做的工作，不要求固定关键词、字段标签、顺序或一条消息说完。分条填写也可使用，但仅是可选方式。工时来自用户明确提供的时长或起止时间，守岸人负责提取、匹配任务和整理措辞。

以下仅为示例，不代表用户当天实际完成的工作，也不构成提交指令：

> 今天 APS 调了排产算法，又修了扫描问题，一共三个半小时。采购筛选改了两小时，帮我整理一下报工。

守岸人检索 ERP 任务、确认唯一匹配后，内部统一整理为“日期、项目、任务 ID/名称、工时、工作内容”，向用户展示业务草稿，例如：

```text
日期：明确的当天日期

项目：光拓智能日常
任务：aps自动排产系统调整
工时：3.5小时
内容：调整排产算法，修复扫描问题。

项目：采购筛选对应的项目（匹配后填写）
任务：采购筛选对应的 ERP 任务（匹配后填写）
工时：2小时
内容：修改采购列表筛选功能。

本次合计：5.5小时
当天已报：读取 ERP 后显示
提交后当天合计：核验后显示，不得超过8小时
```

任务尚未唯一匹配、日期或工时有疑问的条目必须标记待补充，不得以示例占位值进入提交阶段。用户仍可用自然语言修改草稿，例如“APS 实际用了四小时”“刚才采购那条先不报”，无需重新填写整份表单。

输入处理约定：

- 从自然语言提取项目/任务线索、日期、时长及工作内容，不要求用户复制 ERP 原名。简称和描述用于检索候选，只有唯一匹配才绑定真实 `taskId`，否则通过现有 `ask_user` 追问。
- 未提项目时通过任务检索补全；匹配存在歧义时补问。项目不是额外强制的 ERP 报工字段。
- “半小时”“三个半小时”等明确时长可换算为 0.5、3.5 小时；明确、无重叠且休息信息清楚的起止时间可计算工时。缺时长、“忙了一上午”“三四个小时”、休息不明或区间冲突时补问，不能自行猜测、平均分摊、四舍五入或补满 8 小时。
- “大约两小时”等带估计含义的时长可作为待确认候选，在草稿中明确标注，提交前确认数值，不直接当成已确定事实。
- 同时描述多个任务但只提供总时长时，保留总时长并追问各任务分配，不能按任务数平均分摊或在每个任务重复填入总时长。
- 工作内容可以改善表达，但不得增加用户未提供的完成结果、数量或工作事项。
- 消息条数不等于报工记录数。将同一待确认草稿中的补充与更正关联到相应条目，不把“改成四小时”当作额外新增四小时。更正对象不明确时先补问。
- 同一天同任务的多件工作，归属和总时长清楚时可建议合成一条，在预览中展示；用户明确要求分别记录则保留多条，时间重叠或分配不清时不能静默合并。
- 只有用户提出整理/报工意图后才进入该工作流，普通聊天中的工作描述不自动提交。“整理一下”只生成草稿，正式提交仍需确认；已经提交的条目收到更正时不得自动追加抵消记录或直接修改历史记录。
- 本批重复条目、已经存在的同日同任务同工时同内容记录应提示核对，不能仅凭文本相同就自动新增，也不能把合理的第二次报工直接丢弃。

## 3. 拟实现的校验与执行行为

1. 复用有效登录会话；需要登录时定位账号、密码和验证码控件。每次只识别当次验证码图片，识别后的算式由受限算术解析计算；刷新后丢弃旧答案，设置重试上限并支持人工接管。
2. 从当前报工对话整理结构化草稿，保留各条目对应的用户原话；读取当前登录用户与其可操作任务，用项目及真实任务 ID 绑定草稿。只补问影响正确提交的缺失项，优先一次问清。
3. 读取本人指定日期、所有任务的报工明细，完整处理分页。已有工时无法完整核对时停止提交。
4. 校验小时数。按本地 ERP 输入控件，单条最少 0.5 小时、最多一位小数；本批及当天累计不得超过 8 小时。非数字、非有限值、额外精度、负值和零均不可静默修正。小时求和应转换成整数分钟，避免浮点误差。
5. 显示明确日期、项目、任务、每条工时、工作内容、当天已报、本次新增及提交后合计。复用现有工具预览和确认流程。
6. 用户确认后重新核对已有记录与任务状态。草稿内容、日期、身份或影响本次提交的已有记录发生变化时，重新展示预览，不使用过期确认。
7. 按“实际工时 → 新增报工 → 日期/工时/内容 → 确定”逐条执行；支持取消，不在取消后继续发起新增。
8. 保存后回查新增记录 ID、用户、任务、日期、工时及内容，关闭外层工时记录弹窗，再核对任务累计实际工时。点击成功提示本身不构成完成证据。
9. 超时、断网、重启或部分成功时保留逐条结果；结果不明的记录先回查，不自动重放新增。无法唯一确认的结果标为待核验，不得声称整批成功。

首版只针对用户明确确认的新增报工。历史记录修改/删除、后台定时提交和代其他用户报工均不由本工作流触发。

## 4. 本地 ERP 源码核查事实

以下路径均相对于 `D:\erp`。本地源码与已部署网站的版本一致性仍需集成验收确认。

- `ruoyi-ui/src/views/login.vue`：账号、密码、验证码输入框；验证码图片类名 `.login-code-img`，点击及登录失败后会刷新，图片与 `uuid` 配对。
- `ruoyi-ui/src/api/login.js`：登录参数 `username/password/code/uuid`；当前用户信息通过 `getInfo` 获取。凭据与 token 必须留在受控配置或浏览器会话中，不进入对话、日志和截图证据。
- `ruoyi-ui/src/views/business/taskboard/index.vue`：任务行具有 `data-task-block` 对应真实 `taskId`；初始执行人筛选为当前用户，并非按“今天”筛选任务。报工日期与任务开始日期、截止日期需区分。
- 同一页面工时控件为 `min=0.5`、`max=24`、`precision=1`、`step=0.5`，未设置 `step-strictly`。按钮每次增减 0.5，但没有限定手动输入只能是 0.5 的倍数。用户的每日 8 小时限制需要另外校验。
- 同一页面新增字段为 `taskId/taskName/workDate/workHour/workContent/ownerId`，`ownerId` 取当前用户；任务名称用于展示，任务标识用于关联。
- `ruoyi-ui/src/api/business/timeEntry.js`：新增调用 `POST /business/time-entry`，列表为 `GET /business/time-entry/list`，明细为 `GET /business/time-entry/{id}`。`workReport.js` 是汇总查询，不是新增报工入口。
- `ruoyi-admin/src/main/java/com/ruoyi/web/controller/business/BizTimeEntryController.java` 与 `ruoyi-business/src/main/resources/mapper/business/BizTimeEntryMapper.xml`：列表支持 `ownerId` 与 `params.beginTime/params.endTime` 日期筛选，且有分页。看板工时弹窗默认仅按任务查询，不能用它的未筛选总和代替本人当天工时。
- `ruoyi-business/src/main/java/com.ruoyi.business/service/impl/BizTimeEntryServiceImpl.java`：新增及任务实际工时重新汇总处于同一事务；该任务实际工时是全部历史报工累计值。
- 新增返回普通成功/失败响应，不返回新增记录 ID；需提交前后回查。已检查的新增路径没有每日 8 小时校验或业务幂等键。
- 看板保存成功先刷新报工列表，关闭外层工时记录弹窗后才重新获取任务、更新实际工时显示。

集成应扩展守岸人现有工具注册、权限确认、TaskRun、取消与证据机制。浏览器业务提交须有独立高风险工具契约；禁止仅把通用“点击”视为无业务副作用的动作。

本机串行与提交前回查不能保证其他客户端同时报工时的全局原子 8 小时限制。当前 ERP 未提供这项服务端保证，验收时须明确并发边界；发现并发变更需停止并核对。若要求全客户端强制保证，须单独设计 ERP 服务端校验，不能宣称浏览器自动化已经解决。

## 5. 后续验收场景（尚未执行）

- 自然对话、分条描述与可选字段格式表达同一事实时，得到一致的结构化草稿；不因缺少固定标签拒绝理解。
- “三个半小时”正确提取为 3.5；“一上午”触发补问；多个任务只给总时长时不擅自分配。
- 同一对话分多次补充、更正、移除待报条目时更新原草稿，不重复新增或继续使用旧确认。
- 普通工作闲聊不自动提交；已提交记录的后续更正不自动改写历史报工。
- 本日已报 7.5 小时，新报 0.5 小时通过；新报 1 小时拒绝。
- 多项目、多任务共同占用本日 8 小时额度；历史累计和其他用户工时不计入本人的本日限额。
- 可输入 0.5 小时；一位小数、最小值与超额校验遵循上文约定。
- 缺工时、任务重名、任务不可操作、日期跨午夜、分页未读全时不能误报成功。
- 验证码刷新、识别错误、密码错误、会话过期、用户取消均有明确退出或接管路径。
- 重复消息、新对话重试、提交成功但响应超时、部分成功后重启均不自动重复新增。
- 默认主题及替代主题、Electron 实际窗口、工具契约测试按开发契约完成；自动化测试仅使用模拟 ERP 和临时数据。
- 在用户本地配置凭据，并确定测试任务或核对真实报工草稿后，再完成真实环境验收。
