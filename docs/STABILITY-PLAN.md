# The Shorekeeper 稳定化计划

> 版本：0.1.29
> 对应应用：1.3.0
> 日期：2026-09-13
> 状态：S0-S5、H1-H2、H3 自动化和 H4 打包工程已收口；等待实机、真实云账号与代码签名验收
> 目标：在继续扩展私人助理能力前，先把数据库、Agent 运行时、工具/技能、知识库与工作区、人设助理化路线稳定下来。私人云端小模型只作为后续想法，不纳入本轮范围。

---

## 1. 背景

The Shorekeeper 已经具备私人助理的主要底座：流式对话、工具调用、长期记忆、Worldbook、RAG、MCP、技能系统、多窗口、定时任务、文档工具与语音能力。

下一阶段的目标不是继续堆功能，而是让这些能力形成稳定、可维护、可长期使用的系统。尤其在高频使用、持续扩充知识库和工作区文档后，数据库、检索、工具权限和错误恢复会成为核心风险。

如果项目后期运行顺利，可以再考虑租用云端服务器部署私人小模型。那是 S6 的后续想法，不是本轮稳定化的完成条件。当前目标形态仍是本地桌面助理：会话、记忆、知识库原文、工作区和工具执行默认留在本机。

本计划用于指导 M1-M7 之后的稳定化阶段。

---

## 2. 稳定化原则

1. **先审计，再重构**：不凭直觉大换技术栈，先确认真实风险和数据规模。
2. **先收口边界，再扩功能**：Agent、工具、技能、数据库、调度、语音各自有清晰责任。
3. **私人数据优先可靠**：会话、记忆、知识库、任务和配置必须可备份、可迁移、可恢复。
4. **工具调用可解释**：每个工具的输入、输出、权限、失败原因都应可追踪。
5. **人设服务于办事**：守岸人的表达风格要稳定，但不能牺牲任务完成度和事实准确性。
6. **主动性受边界约束**：定时、自动化和后台任务必须有明确权限与降噪规则。
7. **模型服务可替换**：Agent 不绑定某一家云服务或某一个模型，自建模型通过统一协议和能力验收后即可切换。

### 2.1 稳定性复审方法

早期验收主要覆盖已知功能路径、取消/超时和模块接口，测试桩通常返回符合协议的理想数据。这能证明已有契约没有回归，但不能证明边界已经穷尽。2026-09-13 的复审发现，运行中切换配置、供应商畸形调用编号、超长定时器、同任务重入、握手后断线和自然播放后的资源回收都没有进入原验收矩阵；因此旧文档对“已完成”的表述过于绝对。

后续每个模块固定按六类边界复审，不再以测试数量代替覆盖质量：

1. 正常路径与真实产物。
2. 运行中状态突变和配置切换。
3. 畸形、缺失、超大或恶意输入。
4. 长时间、系统计时上限和容量边界。
5. 重复请求、并发、重入和幂等。
6. 成功、失败、取消、窗口关闭及应用退出后的资源释放。

“阶段完成”表示上述已知边界有证据和回归，不表示以后不可能发现新问题；新发现必须先补失败样例，再修实现并更新验收矩阵。

### 2.2 2026-09-20 全仓稳定性复审

本轮不增加功能，按并发、缓存、恢复与失败可见性复审现有路径，并收口九个已确认缺口：

- 同一音频同一配置只允许一个带 `attempt_id` 的转写尝试认领；旧尝试不能覆盖重试结果，缓存命中仍返回产物证据。
- 视觉 sidecar 记录每张源图 SHA-256；图片内容变化或删除后不再误命中旧答案。
- 工作区同目标写入进程内串行，确认后的写入在提交前于锁内复核 revision；过期预览不落文件或备份。
- 查询 CSV 名称加入查询记录 ID；同秒同摘要的查询不再互相覆盖，启动时统一把遗留 `query_runs.running` 收口为 `cancelled`。
- 一次性定时任务异常后禁用并保留失败事实，不在副作用未知时自动重放，也不留下“启用但无计时器”的假状态。
- 主动服务停机向运行周期传播 `AbortSignal`；异步弹窗返回后先检查取消，再写投递账本，避免关库后续写。
- 聊天发送 IPC 拒绝会撤回未持久化的乐观消息并展示错误，不再产生未处理 Promise rejection。

每一项均新增原始失败路径的回归测试；最终命令结果以本轮交付记录为准。

## 3. 当前判断

### 3.1 已接近私人助理底座

- Agent 循环和工具调用已经落地。
- 长期记忆、用户画像、Worldbook 已有数据模型。
- RAG 知识库已经能导入文档并检索回答。
- 技能系统和 MCP 为后续扩展提供了入口。
- 定时任务、多窗口、语音让它更像常驻桌面助理，而不是网页聊天 Demo。

### 3.2 原不稳定点（S0-S5 已收口）

审计当时的风险已经按阶段落地，不再作为当前阻断项：

- **数据库路线**：生产运行时已切换到 `better-sqlite3`（活动库 `shorekeeper.native.db`）。`sql.js` 只保留为回滚源和双 adapter 测试，不再是默认主库。
- **主进程复杂度**：Agent、数据库、工具、调度已收口到 IPC、Repository 和领域边界；业务层不再直接持有 sql.js。
- **工具/技能协议**：S3 已统一权限、写入确认、错误分类和技能白名单。
- **知识库增长**：S4 已补齐导入回滚、重建、隔离删除和 RAG 注入模式。
- **私人助理体验**：S5 已落地会话模式、记忆候选/已保存记忆管理，以及主动性降噪。
- **模型服务边界**：现有 OpenAI-compatible / Anthropic-like 适配的运行快照、瞬时重试、错误脱敏和协议一致性已补强；统一能力声明、备用模型和云端隐私约束仍留给后续想法（S6）。

剩余项见第 5 节“可选后续演进”，均不阻断框架稳定化收口。

### S2：Agent 运行时稳定化

**目标**：让每一次对话运行可控、可取消、可恢复、可排查。

S2 分为 **5 个实施阶段 + 1 个总验收阶段**。每阶段都先补行为契约和测试，再改运行时代码，避免为了扩展私人助理能力而继续累积隐式状态。

**当前状态**：S2.1-S2.6 已全部完成；2026-09-13 复审又补齐模型 profile/协议原子快照、429/5xx 瞬时重试、上游错误正文隔离、重复工具调用防副作用、工具结果滚动预算和单轮工具洪泛保护。Agent 已具备统一生命周期、全链路取消与超时、脱敏运行诊断、上下文预算、后台任务隔离和退出收敛。可复用验收入口为 `pnpm test:s2`，详细场景见 `docs/S2-ACCEPTANCE.md`。

#### S2.1：运行生命周期与责任边界

**目标**：明确一次 run 从接收消息到结束的单一状态流转。

- 梳理 `orchestrator`、`loop`、`context-builder`、`stable-context`、Electron IPC 的边界。
- 固化状态：`created`、`running`、`waiting_tool`、`finalizing`、`finished`、`cancelled`、`error`。
- 保证普通对话、定时任务、语音通话都有统一的开始、结束和异常清理路径。
- 修复运行中途预处理、权限等待或后台任务异常导致的锁、presence 或会话状态残留。

**验收**：每个 run 恰好有一个终态；异常不会留下不可发送消息的会话锁，也不会写入半截 assistant 消息。

#### S2.2：取消、超时与资源回收

**目标**：取消是真正停止本轮工作，而不是只停止界面事件。

- 统一 `AbortSignal` 从 IPC 贯穿模型流、工具、MCP、Embedding、语音播放和通话。
- 增加模型请求、单个工具、MCP 请求和后台会话任务的超时策略。
- 区分用户取消、超时、网络失败、权限拒绝和内部异常。
- 确保取消后 reader、定时器、权限请求、音频队列和 session run lock 都会释放。

**验收**：取消或超时后不会继续写入 assistant 回复；下一条消息可以立即运行；外部请求不会无限悬挂。

**阶段结果**：模型、工具、权限、MCP、语音、RAG/Embedding 和后台任务均有取消或超时路径；取消后的 assistant 持久化、归档导入和定时提醒快捷路径已补齐边界检查。AI 提醒文案增加 30 秒硬超时与静态回退；模型初始连接遇到网络失败、429 或可恢复 5xx 时只在尚未产生输出前重试，避免重复内容。语音复审补齐 STT 握手后断线、并发/过期启动失效、TTS 中途失败降级、异常事件流终止和应用退出清理。

#### S2.3：运行可观测性与错误恢复

#### S2.5：运行恢复与后台任务隔离

**目标**：把记忆提取、会话压缩等后台工作与主 run 解耦，同时保证一致性。

**阶段结果**：主 run 在回复持久化并进入成功终态后才调度压缩和记忆提取，后台失败只追加到原 run 诊断，不会反向改变主 run。后台任务按会话串行、单次最多 60 秒、最多执行 1 次；不自动重试含持久化副作用的任务。模型切换会取消旧配置下的后台任务。应用退出会停止接收新 run、停止调度和权限等待、取消前台/后台工作、限时等待底层 Promise 收敛，再异步 checkpoint 并关闭数据库。普通聊天、定时 Agent 和语音使用同一会话锁，释放操作校验控制器所有权；语音中断不会误删后续锁，也不会取消同会话中不属于该通话的文字 run。

**验收**：后台任务失败不破坏对话；应用重启后没有悬挂状态；定时任务和语音运行不会与普通对话互相污染。

- 建立私人助理模式：
  - `focus`: 帮你推进任务
  - `organize`: 整理资料和知识库
  - `review`: 审核计划、文档、代码或待办
  - `companion`: 更轻陪伴和情绪支持

**验收**：

- 常见事务不需要反复解释背景。
- 她能稳定区分“陪聊”和“办事”。
- 主动提醒有帮助，不制造噪音。

### S6：后续想法（不在本轮范围）

S5 落地后，框架稳定化阶段即结束。下面只是以后若要自建推理服务时的方向备忘，当前不推进、不定工期、不作为验收项。

**若以后要做**：在不迁移本地私人数据和工具执行权的前提下，让 The Shorekeeper 可以切换到自建云端小模型。推荐拓扑仍是桌面端管数据与工具，云端只做推理。

**推荐拓扑**：

```text
The Shorekeeper 桌面端
  ├─ 本地：SQLite、记忆、知识库、工作区、技能、权限、工具执行
  └─ HTTPS：发送最小必要上下文
        ↓
私人云端推理服务
  └─ 小模型：对话、推理、Function Calling
```

**任务**：

- 固化模型服务最小协议：
  - OpenAI-compatible Chat Completions
  - 流式文本输出
  - Function Calling / Tool Calling
  - 多轮工具结果回注
  - `AbortSignal` 取消与请求超时
  - token usage 返回或可估算
- 增加模型能力描述：
  - 是否支持工具调用
  - 是否支持流式输出
  - 最大上下文长度
  - 是否支持 reasoning 内容
  - 并发和单次输出限制
- 建立模型兼容验收集：
  - 守岸人人设遵循
  - 中文指令理解
  - 单次与连续工具调用
  - RAG 检索后回答
  - 长会话摘要续聊
  - 错误参数修正和工具失败恢复
- 保持 Embedding 服务独立：
  - 聊天模型与 Embedding 模型可使用不同服务
  - 更换聊天模型不强制重建知识库向量
  - 更换 Embedding 模型时沿用现有重嵌入流程
- 增加连接与故障策略：
  - 服务健康检查
  - HTTPS 与访问令牌
  - 请求限流和并发上限
  - 超时、重试与熔断
  - 私人模型不可用时切回已配置的备用模型
- 明确隐私边界：
  - 不上传完整数据库和工作区目录
  - 只发送本轮必要的记忆、RAG 片段和工具结果
  - 云端日志默认脱敏，不记录 API Key、完整文档和长期记忆
  - 服务端数据保留策略必须可配置和关闭
- 部署 PoC 时再选择推理引擎和模型，不在当前稳定化阶段锁定具体方案。

**进入条件（仅在真正启动该想法时）**：

- S0-S4 的稳定性问题已基本收口。
- 至少三个高频私人助理场景已有固定验收样例。
- 已明确预算、并发需求、目标延迟和可接受的模型能力下限。

**验收**：

- 切换到私人模型只需要修改模型配置，不需要改 Agent 和工具代码。
- 私人模型能够稳定完成核心对话、RAG 和工具调用验收集。
- 云端服务不可用时，桌面端能明确报错或切换备用模型，不破坏会话状态。
- 本地数据库、原始知识库和工作区文件不会被整体上传。

## 7. 私人模型路线建议（后续想法）

这不是本轮稳定化的工作项。当前架构已经走 OpenAI-compatible 接口，所以以后若要自建模型，不需要先重写 Agent。现在不租服务器、不定模型和推理引擎。

1. **本地数据层保持独立**
   SQLite、记忆、知识库、工作区和工具执行继续由桌面端管理。

2. **模型接口保持标准化**
   优先以 OpenAI-compatible 接口作为自建服务接入面，模型差异由现有 adapter 和后续 capability profile 消化。

3. **聊天与 Embedding 分离**
   私人小模型可以只负责对话和工具决策，向量生成继续使用独立 Embedding 服务。

4. **先用验收集选模型**
   不只比较参数量和聊天观感，应以工具调用成功率、中文遵循、RAG 回答质量、延迟和运行成本判断是否可用。

5. **最后再决定是否迁移更多服务**
   云端模型不等于云端数据库。只有出现多设备共享需求时，才单独评估同步层或云端数据服务。
