# The Shorekeeper 稳定化计划

> 版本：0.1.19
> 日期：2026-09-11
> 状态：执行中
> 目标：在继续扩展私人助理能力前，先把数据库、Agent 运行时、工具/技能、知识库与工作区、人设助理化路线稳定下来，并为后期部署私人云端小模型保留清晰的接入边界。

---

## 1. 背景

The Shorekeeper 已经具备私人助理的主要底座：流式对话、工具调用、长期记忆、Worldbook、RAG、MCP、技能系统、多窗口、定时任务、文档工具与语音能力。

下一阶段的目标不是继续堆功能，而是让这些能力形成稳定、可维护、可长期使用的系统。尤其在高频使用、持续扩充知识库和工作区文档后，数据库、检索、工具权限和错误恢复会成为核心风险。

如果项目后期运行顺利，计划租用云端服务器部署私人小模型。目标形态是“本地桌面助理 + 私人云端推理服务”：会话、记忆、知识库原文、工作区和工具执行默认留在本机，云端模型只接收完成当前任务所需的最小上下文并负责推理。

本计划用于指导 M1-M7 之后的稳定化阶段。

---

## 2. 稳定化原则

1. **先审计，再重构**：不凭直觉大换技术栈，先确认真实风险和数据规模。
2. **先收口边界，再扩功能**：Agent、工具、技能、数据库、调度、语音各自有清晰责任。
3. **私人数据优先可靠**：会话、记忆、知识库、任务和配置必须可备份、可迁移、可恢复。
4. **工具调用可解释**：每个工具的输入、输出、权限、失败原因都应可追踪。
5. **人设服务于办事**：守岸人的表达风格要稳定，但不能牺牲任务完成度和事实准确性。
6. **主动性受边界约束**：定时、自动化和后台任务必须有明确权限与降噪规则。
7. **模型服务可替换**：Agent 不绑定某一家云服务或某一个模型，自建模型通过统一协议和能力验收后即可切换。

---

## 3. 当前判断

### 3.1 已接近私人助理底座

- Agent 循环和工具调用已经落地。
- 长期记忆、用户画像、Worldbook 已有数据模型。
- RAG 知识库已经能导入文档并检索回答。
- 技能系统和 MCP 为后续扩展提供了入口。
- 定时任务、多窗口、语音让它更像常驻桌面助理，而不是网页聊天 Demo。

### 3.2 主要不稳定点

- **数据库路线**：当前 `sql.js` 适合免 native 打包，但长期高频写入、大知识库和崩溃恢复需要重新评估。
- **主进程复杂度**：Agent、DB、工具、调度、窗口、语音都在主进程附近，边界需要收紧。
- **工具/技能协议**：工具结果、权限、错误、日志、技能白名单需要统一标准。
- **知识库增长**：文档 chunk、embedding、索引、重建、删除和版本管理需要更完整的生命周期。
- **私人助理体验**：需要把人设、记忆、任务、主动提醒组合成高频闭环，而不是零散能力。
- **模型服务边界**：当前已有 OpenAI-compatible / Anthropic-like 适配，但还缺少统一的模型能力声明、兼容性测试、故障回退和云端隐私约束。

- 梳理主进程模块依赖：`electron/`、`src/agent/`、`src/tools/`、`src/db/`、`src/rag/`、`src/voice/`。

### S2：Agent 运行时稳定化

**目标**：让每一次对话运行可控、可取消、可恢复、可排查。

S2 分为 **5 个实施阶段 + 1 个总验收阶段**。每阶段都先补行为契约和测试，再改运行时代码，避免为了扩展私人助理能力而继续累积隐式状态。

**当前状态**：S2.1-S2.6 已全部完成；Agent 已具备统一生命周期、全链路取消与超时、脱敏运行诊断、上下文预算、后台任务隔离和退出收敛。可复用验收入口为 `pnpm test:s2`，详细场景见 `docs/S2-ACCEPTANCE.md`。

#### S2.1：运行生命周期与责任边界

**目标**：明确一次 run 从接收消息到结束的单一状态流转。

- 梳理 `orchestrator`、`loop`、`context-builder`、`stable-context`、Electron IPC 的边界。
- 固化状态：`created`、`running`、`waiting_tool`、`finalizing`、`finished`、`cancelled`、`error`。
- 保证普通对话、定时任务、语音通话都有统一的开始、结束和异常清理路径。
- 修复运行中途预处理、权限等待或后台任务异常导致的锁、presence 或会话状态残留。

**验收**：每个 run 恰好有一个终态；异常不会留下不可发送消息的会话锁，也不会写入半截 assistant 消息。

#### S2.2：取消、超时与资源回收

**目标**：取消是真正停止本轮工作，而不是只停止界面事件。

- 统一 `AbortSignal` 从 IPC 贯穿模型流、工具、MCP、Embedding、语音播放和通话。
- 增加模型请求、单个工具、MCP 请求和后台会话任务的超时策略。
- 区分用户取消、超时、网络失败、权限拒绝和内部异常。
- 确保取消后 reader、定时器、权限请求、音频队列和 session run lock 都会释放。

**验收**：取消或超时后不会继续写入 assistant 回复；下一条消息可以立即运行；外部请求不会无限悬挂。

**阶段结果**：模型、工具、权限、MCP、语音、RAG/Embedding 和后台任务均有取消或超时路径；取消后的 assistant 持久化、归档导入和定时提醒快捷路径已补齐边界检查，并通过自动化回归。

#### S2.3：运行可观测性与错误恢复

**目标**：能回答“哪一次 run、在哪一步、为什么失败”。

**阶段结果**：已接入 run 终态结构化摘要和活动级记录，覆盖模型轮次、工具执行、权限确认、消息持久化与后台会话任务的状态、耗时和脱敏错误分类；记录 `runId`、`sessionId`、模型、活动技能、终态阶段、工具调用统计和 token 用量。最近 100 条脱敏诊断可通过主进程只读接口按 `runId` 查询，聊天界面会展示恢复建议与运行编号。日志不记录消息正文、工具参数、API Key 或堆栈。同一会话的压缩与记忆提取已改为串行队列，退出时会中止所有活动及排队任务。

- 统一运行事件和日志字段：`runId`、`sessionId`、`modelId`、`activeSkillIds`、阶段、耗时、工具调用、token usage、错误摘要。
- 为模型流、工具调用、权限等待和持久化分别记录开始/结束/失败。
- 统一面向用户的错误分类与恢复提示，避免把内部堆栈直接暴露给界面。
- 为失败 run 保留可诊断信息，但不得记录 API Key、完整隐私文档或未脱敏长期记忆。

**验收**：一次失败可以通过 `runId` 定位；用户能看到下一步动作；日志不会泄露敏感数据。

#### S2.4：上下文预算与长会话控制

**目标**：让上下文增长可预测，避免长会话拖慢或超出模型限制。

**阶段结果**：已增加统一输入 Token 预算（默认 24,000，可在性能设置中调整），system prompt 按稳定前缀、技能、工具、摘要、Worldbook、RAG、长期记忆、画像和目录的优先级进行去重、裁剪与降级；历史消息同时受条数和 Token 预算约束，始终优先保留最新消息。预算估算、裁剪数量、丢弃/截断块和超预算量会写入 run 诊断。会话压缩会记录 `model_unavailable`、`below_threshold`、`already_compressed`、`empty_summary` 或 `compressed` 原因，`catalog`、`auto`、`tool` 三种 RAG 模式已有独立预算契约测试。

- 固定最近消息、摘要、Worldbook、长期记忆和 RAG 的预算顺序与上限。
- 对稳定提示、技能、工具说明和动态上下文去重，避免重复注入。
- 明确 `catalog`、`auto`、`tool` 三种 RAG 注入模式的预算行为。
- 记录上下文估算和压缩原因，为后续模型切换保留可比较指标。

**验收**：连续长对话不会无限膨胀；压缩后语义连续；超预算时有可解释的降级顺序。

#### S2.5：运行恢复与后台任务隔离

**目标**：把记忆提取、会话压缩等后台工作与主 run 解耦，同时保证一致性。

**阶段结果**：主 run 在回复持久化并进入成功终态后才调度压缩和记忆提取，后台失败只追加到原 run 诊断，不会反向改变主 run。后台任务按会话串行、单次最多 60 秒、最多执行 1 次；不自动重试含持久化副作用的任务。模型切换会取消旧配置下的后台任务。应用退出会停止接收新 run、停止调度和权限等待、取消前台/后台工作、限时等待底层 Promise 收敛，再异步 checkpoint 并关闭数据库。普通聊天、定时 Agent 和语音使用同一会话锁，释放操作校验控制器所有权；语音中断不会误删后续锁，也不会取消同会话中不属于该通话的文字 run。

- 区分主 run 成功与后台记忆/摘要任务成功，不因后台失败误报主 run 失败。
- 为后台任务增加超时、重试上限、失败记录和会话级串行约束。
- 处理应用退出、数据库关闭和模型切换时的后台任务收尾。
- 为定时任务和语音通话复用同一套运行状态与错误策略。

**验收**：后台任务失败不破坏对话；应用重启后没有悬挂状态；定时任务和语音运行不会与普通对话互相污染。

#### S2.6：总体验收

**固定场景**：普通对话、连续工具调用、工具失败、模型超时、用户取消、长会话压缩、定时任务触发、语音中断、应用退出恢复。

**阶段结果（2026-09-11）**：`pnpm test:s2` 固定验收入口覆盖 16 个文件、70 项 S2 专项测试并全部通过；完整 Vitest 回归 95 个文件、380 项测试通过，`pnpm typecheck`、生产构建、Electron 44 runtime smoke 和打包后 native SQLite 探针通过。补充修复了长会话 checkpoint 重复摘要、摘要/记忆抽取输入无上限、超长 RAG 查询、模型流 reader、REST TTS 取消和 Embedding/HyDE 超时边界。活动数据库使用 `better-sqlite3`，`integrity_check` 为 `ok`、15 个 migration 全部 applied；现有 WARNING 仅包括一个历史损坏备份以及开发进程遗留的 WAL/SHM 提醒。

**总验收**：

- Agent 出错不会破坏会话状态。
- 工具或模型失败能给出明确错误和恢复动作。
- 长会话不会无限膨胀上下文。
- 每个 run 都能通过日志和事件追踪到唯一终态。
- S2 验收集可供后续私人小模型兼容性测试复用。

### S3：工具、技能与权限稳定化

**目标**：让技能扩展变得可控，避免工具越多越乱。

**当前状态**：S3.1 已完成，S3.2-S3.6 尚未开始。工具结果已经有统一归一化入口和稳定错误类别；Agent 工具事件、运行诊断和定时提醒快捷路径均使用同一契约。后续阶段继续沿用 `pnpm test:s3` 作为增量验收入口。

#### S3.1：工具结果与错误分类统一

**阶段结果（2026-09-11）**：`ToolResult` 已统一支持 `success`、`output`、`error`、`errorCategory`、`metadata` 和 `artifacts`；新增 malformed result 归一化、错误分类和稳定工具错误构造器。Agent 主执行链和定时提醒快捷路径均经过归一化，运行诊断额外保留 `toolErrorCategory`，不会再只依赖错误文本判断工具失败原因。

**验收**：`pnpm test:s3` 的 S3.1 测试通过；工具失败、超时、权限拒绝、路径越界和外部服务错误均能保留稳定分类，失败结果不会被标记为成功。

**任务**：

- 定义统一工具结果格式：
  - `success`
  - `output`
  - `error`
  - `metadata`
  - `artifacts`
- 定义工具错误分类：
  - 参数错误
  - 权限拒绝
  - 路径越界
  - 网络失败
  - 外部服务失败
  - 内部异常
- 强化权限层：
  - 读文件默认限制工作区
  - 写文件默认确认
  - 网络工具可开关
  - MCP 工具可禁用
  - 高风险自动化必须确认
- 技能系统收口：
  - manual 技能只用于常驻风格/核心行为
  - auto 技能必须有触发词和测试用例
  - 技能不得重复注入全局工具规则
  - 技能白名单并集逻辑保持可测试
- 建立工具验收样例：
  - 文件读取
  - 文件写入并读回校验
  - 文档生成
  - Excel 读取
  - RAG 检索
  - 定时任务创建

**验收**：

- 新增技能时有模板和验收清单。
- 工具失败时不会表现成“已完成”。
- 权限边界可被测试覆盖。

### S6：私人云端小模型接入准备（后期）

**目标**：在不迁移本地私人数据和工具执行权的前提下，让 The Shorekeeper 可以切换到自建云端小模型。

**推荐拓扑**：

```text
The Shorekeeper 桌面端
  ├─ 本地：SQLite、记忆、知识库、工作区、技能、权限、工具执行
  └─ HTTPS：发送最小必要上下文
        ↓
私人云端推理服务
  └─ 小模型：对话、推理、Function Calling
```

**任务**：

- 固化模型服务最小协议：
  - OpenAI-compatible Chat Completions
  - 流式文本输出
  - Function Calling / Tool Calling
  - 多轮工具结果回注
  - `AbortSignal` 取消与请求超时
  - token usage 返回或可估算
- 增加模型能力描述：
  - 是否支持工具调用
  - 是否支持流式输出
  - 最大上下文长度
  - 是否支持 reasoning 内容
  - 并发和单次输出限制
- 建立模型兼容验收集：
  - 守岸人人设遵循
  - 中文指令理解
  - 单次与连续工具调用
  - RAG 检索后回答
  - 长会话摘要续聊
  - 错误参数修正和工具失败恢复
- 保持 Embedding 服务独立：
  - 聊天模型与 Embedding 模型可使用不同服务
  - 更换聊天模型不强制重建知识库向量
  - 更换 Embedding 模型时沿用现有重嵌入流程
- 增加连接与故障策略：
  - 服务健康检查
  - HTTPS 与访问令牌
  - 请求限流和并发上限
  - 超时、重试与熔断
  - 私人模型不可用时切回已配置的备用模型
- 明确隐私边界：
  - 不上传完整数据库和工作区目录
  - 只发送本轮必要的记忆、RAG 片段和工具结果
  - 云端日志默认脱敏，不记录 API Key、完整文档和长期记忆
  - 服务端数据保留策略必须可配置和关闭
- 部署 PoC 时再选择推理引擎和模型，不在当前稳定化阶段锁定具体方案。

**进入条件**：

- S0-S4 的稳定性问题已基本收口。
- 至少三个高频私人助理场景已有固定验收样例。
- 已明确预算、并发需求、目标延迟和可接受的模型能力下限。

**验收**：

- 切换到私人模型只需要修改模型配置，不需要改 Agent 和工具代码。
- 私人模型能够稳定完成核心对话、RAG 和工具调用验收集。
- 云端服务不可用时，桌面端能明确报错或切换备用模型，不破坏会话状态。
- 本地数据库、原始知识库和工作区文件不会被整体上传。

## 6. 数据库路线建议

根据当前高频使用和知识库扩展计划，原生 SQLite 生产迁移已完成。活动数据库为 `shorekeeper.native.db`，原 `shorekeeper.db` 保留为可校验的 sql.js 回滚源。

1. **保留 `sql.js` 回滚能力**
   原主库、引擎标记和 `pre-native` 备份共同构成回滚路径；正常启动不再默认选择 sql.js。

2. **完成双 adapter 数据边界**
   Repository 抽象、正式 better-sqlite3 adapter 和双引擎合约测试已经完成。

3. **迁移并验证数据库副本**
   自动备份、副本迁移、native FTS 补齐、业务表/BLOB 摘要和回滚演练已经通过。

4. **完成安装包验证后原子切换**
   native 依赖、Electron 打包、升级覆盖、异常恢复和真实使用验收均已通过；后续只需在版本升级或数据库结构变化时重复健康检查与备份流程。

## 7. 私人模型路线建议

私人模型方向不需要现在立即租服务器或确定模型。当前只需要保证架构不把 Agent 绑定到百炼或其他单一服务：

1. **本地数据层保持独立**
   SQLite、记忆、知识库、工作区和工具执行继续由桌面端管理。

2. **模型接口保持标准化**
   优先以 OpenAI-compatible 接口作为自建服务接入面，模型差异由现有 adapter 和后续 capability profile 消化。

3. **聊天与 Embedding 分离**
   私人小模型可以只负责对话和工具决策，向量生成继续使用独立 Embedding 服务。

4. **先用验收集选模型**
   不只比较参数量和聊天观感，应以工具调用成功率、中文遵循、RAG 回答质量、延迟和运行成本判断是否可用。

5. **最后再决定是否迁移更多服务**
   云端模型不等于云端数据库。只有出现多设备共享需求时，才单独评估同步层或云端数据服务。
