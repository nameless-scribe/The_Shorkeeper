# The Shorekeeper 稳定化计划

> 版本：0.1.1  
> 日期：2026-09-10  
> 状态：草案  
> 目标：在继续扩展私人助理能力前，先把数据库、Agent 运行时、工具/技能、知识库与工作区、人设助理化路线稳定下来，并为后期部署私人云端小模型保留清晰的接入边界。

---

## 1. 背景

The Shorekeeper 已经具备私人助理的主要底座：流式对话、工具调用、长期记忆、Worldbook、RAG、MCP、技能系统、多窗口、定时任务、文档工具与语音能力。

下一阶段的目标不是继续堆功能，而是让这些能力形成稳定、可维护、可长期使用的系统。尤其在高频使用、持续扩充知识库和工作区文档后，数据库、检索、工具权限和错误恢复会成为核心风险。

如果项目后期运行顺利，计划租用云端服务器部署私人小模型。目标形态是“本地桌面助理 + 私人云端推理服务”：会话、记忆、知识库原文、工作区和工具执行默认留在本机，云端模型只接收完成当前任务所需的最小上下文并负责推理。

本计划用于指导 M1-M7 之后的稳定化阶段。

---

## 2. 稳定化原则

1. **先审计，再重构**：不凭直觉大换技术栈，先确认真实风险和数据规模。
2. **先收口边界，再扩功能**：Agent、工具、技能、数据库、调度、语音各自有清晰责任。
3. **私人数据优先可靠**：会话、记忆、知识库、任务和配置必须可备份、可迁移、可恢复。
4. **工具调用可解释**：每个工具的输入、输出、权限、失败原因都应可追踪。
5. **人设服务于办事**：守岸人的表达风格要稳定，但不能牺牲任务完成度和事实准确性。
6. **主动性受边界约束**：定时、自动化和后台任务必须有明确权限与降噪规则。
7. **模型服务可替换**：Agent 不绑定某一家云服务或某一个模型，自建模型通过统一协议和能力验收后即可切换。

---

## 3. 当前判断

### 3.1 已接近私人助理底座

- Agent 循环和工具调用已经落地。
- 长期记忆、用户画像、Worldbook 已有数据模型。
- RAG 知识库已经能导入文档并检索回答。
- 技能系统和 MCP 为后续扩展提供了入口。
- 定时任务、多窗口、语音让它更像常驻桌面助理，而不是网页聊天 Demo。

### 3.2 主要不稳定点

- **数据库路线**：当前 `sql.js` 适合免 native 打包，但长期高频写入、大知识库和崩溃恢复需要重新评估。
- **主进程复杂度**：Agent、DB、工具、调度、窗口、语音都在主进程附近，边界需要收紧。
- **工具/技能协议**：工具结果、权限、错误、日志、技能白名单需要统一标准。
- **知识库增长**：文档 chunk、embedding、索引、重建、删除和版本管理需要更完整的生命周期。
- **私人助理体验**：需要把人设、记忆、任务、主动提醒组合成高频闭环，而不是零散能力。
- **模型服务边界**：当前已有 OpenAI-compatible / Anthropic-like 适配，但还缺少统一的模型能力声明、兼容性测试、故障回退和云端隐私约束。

---

## 4. 阶段路线

### S0：稳定化冻结与基线审计

**目标**：先获得真实状态，避免边修边散。

**任务**：

- 固定当前范围：M8 已移除；短期不新增大型功能。
- 跑基线命令：`pnpm typecheck`、`pnpm test`、`pnpm build`。
- 记录当前失败项，区分“已有问题”和“本轮引入问题”。
- 统计数据库规模：会话数、消息数、记忆数、文档数、chunk 数、embedding 体积、DB 文件大小。
- 梳理主进程模块依赖：`electron/`、`src/agent/`、`src/tools/`、`src/db/`、`src/rag/`、`src/voice/`。

**基线结果（2026-09-10）**：

- `pnpm typecheck`：通过。
- `pnpm test`：66 个测试文件、266 个测试全部通过。
- `pnpm build`：通过；渲染端主 JS chunk 约 1.14 MB，代码分包作为后续非阻断优化。

**验收**：

- 形成稳定性审计清单。
- 明确 P0/P1/P2 风险。
- 明确是否需要数据库迁移 PoC。

### S1：数据库与存储稳定化

**目标**：让长期私人数据可靠保存、备份、迁移。

**任务**：

- 评估 `sql.js` 当前风险：
  - DB 文件大小增长速度
  - 高频写入时保存策略
  - 应用异常退出后的恢复能力
  - RAG embedding BLOB 对内存和启动速度的影响
- 定义 Repository 边界：
  - 会话/消息
  - 记忆/用户画像/Worldbook
  - RAG 文档/chunk/embedding
  - 定时任务/用户待办
  - 设置/语音/插件/MCP
- 增加数据库健康检查：
  - migration 状态
  - 表结构版本
  - 关键表计数
  - 最近备份时间
- 增加备份策略：
  - 启动前轻量备份
  - 手动导出
  - migration 前备份
- 做原生 SQLite PoC：
  - 优先评估 `better-sqlite3`
  - 验证 Electron Windows 打包
  - 验证 migration、WAL、备份、读写性能

**数据库决策门槛**：

- 如果 DB 仍小、chunk 少、写入低频：继续 `sql.js`，先补备份和健康检查。
- 如果知识库快速增长、启动变慢、保存成本上升：迁到原生 SQLite。
- 如果未来要多设备同步：再评估 `libSQL` / 云同步方案，不作为当前默认路线。

**验收**：

- 有明确数据库路线结论。
- 无论是否迁移，都有备份、恢复、migration 安全策略。

### S2：Agent 运行时稳定化

**目标**：让每一次对话运行可控、可取消、可恢复、可排查。

**任务**：

- 梳理 `orchestrator`、`loop`、`context-builder`、`stable-context` 的责任边界。
- 统一 run 生命周期：
  - `run_started`
  - context 构建
  - 模型流式输出
  - 工具调用
  - 持久化
  - 记忆提取
  - `run_finished` / `run_error`
- 补齐取消和超时：
  - 模型请求超时
  - 工具调用超时
  - MCP server 超时
  - 语音播放/通话中断
- 建立运行日志：
  - runId
  - sessionId
  - modelId
  - activeSkillIds
  - tool calls
  - token usage
  - error summary
- 稳定上下文预算：
  - 最近消息上限
  - summary 注入
  - RAG 注入模式
  - 技能注入去重

**验收**：

- Agent 出错不会破坏会话状态。
- 工具或模型失败能给出明确错误。
- 长会话不会无限膨胀上下文。

### S3：工具、技能与权限稳定化

**目标**：让技能扩展变得可控，避免工具越多越乱。

**任务**：

- 定义统一工具结果格式：
  - `success`
  - `output`
  - `error`
  - `metadata`
  - `artifacts`
- 定义工具错误分类：
  - 参数错误
  - 权限拒绝
  - 路径越界
  - 网络失败
  - 外部服务失败
  - 内部异常
- 强化权限层：
  - 读文件默认限制工作区
  - 写文件默认确认
  - 网络工具可开关
  - MCP 工具可禁用
  - 高风险自动化必须确认
- 技能系统收口：
  - manual 技能只用于常驻风格/核心行为
  - auto 技能必须有触发词和测试用例
  - 技能不得重复注入全局工具规则
  - 技能白名单并集逻辑保持可测试
- 建立工具验收样例：
  - 文件读取
  - 文件写入并读回校验
  - 文档生成
  - Excel 读取
  - RAG 检索
  - 定时任务创建

**验收**：

- 新增技能时有模板和验收清单。
- 工具失败时不会表现成“已完成”。
- 权限边界可被测试覆盖。

### S4：知识库与工作区稳定化

**目标**：支撑长期扩充文档，不让 RAG 变成不可维护的黑箱。

**任务**：

- 文档导入生命周期：
  - 导入中
  - 已索引
  - 索引失败
  - 需要重建
  - 已删除
- 文档去重：
  - 文件 hash
  - 路径
  - 标题
  - 文档版本
- chunk 管理：
  - chunk 大小和 overlap 固化配置
  - Markdown 感知分块保留
  - 大文档导入进度可见
- embedding 管理：
  - 模型 ID 记录
  - 维度记录
  - 批量重嵌入
  - 失败重试
- 检索质量基线：
  - 准备 10-20 个固定问答样例
  - 对比 `catalog` / `auto` / `tool`
  - 记录召回片段和最终回答质量
- 工作区文档规则：
  - 原始附件保留
  - 生成文件有命名规范
  - 修改文件必须读回确认
  - 重要文件写入前备份

**验收**：

- 知识库可以扩充、删除、重建。
- 检索质量有固定样例可回归。
- 工作区文件不会被误写、覆盖或丢失。

### S5：守岸人私人助理化

**目标**：把技术能力收束成一个稳定的人格化私人助理体验。

**任务**：

- 定义守岸人人设契约：
  - 语气
  - 称呼
  - 办事风格
  - 情绪表达
  - 拒绝和提醒方式
- 定义记忆策略：
  - 什么应该记住
  - 什么不该记住
  - 何时自动提取
  - 何时询问确认
  - 如何编辑/删除记忆
- 定义高频助理场景：
  - 每日计划和晚间总结
  - 工作区文档整理
  - 知识库问答和资料归档
  - 项目计划维护
  - 待办追踪和提醒
  - 文档/表格生成
- 定义主动性边界：
  - 可静默执行的任务
  - 必须提醒的任务
  - 必须确认的任务
  - 不应打扰的时间或场景
- 建立私人助理模式：
  - `focus`: 帮你推进任务
  - `organize`: 整理资料和知识库
  - `review`: 审核计划、文档、代码或待办
  - `companion`: 更轻陪伴和情绪支持

**验收**：

- 常见事务不需要反复解释背景。
- 她能稳定区分“陪聊”和“办事”。
- 主动提醒有帮助，不制造噪音。

### S6：私人云端小模型接入准备（后期）

**目标**：在不迁移本地私人数据和工具执行权的前提下，让 The Shorekeeper 可以切换到自建云端小模型。

**推荐拓扑**：

```text
The Shorekeeper 桌面端
  ├─ 本地：SQLite、记忆、知识库、工作区、技能、权限、工具执行
  └─ HTTPS：发送最小必要上下文
        ↓
私人云端推理服务
  └─ 小模型：对话、推理、Function Calling
```

**任务**：

- 固化模型服务最小协议：
  - OpenAI-compatible Chat Completions
  - 流式文本输出
  - Function Calling / Tool Calling
  - 多轮工具结果回注
  - `AbortSignal` 取消与请求超时
  - token usage 返回或可估算
- 增加模型能力描述：
  - 是否支持工具调用
  - 是否支持流式输出
  - 最大上下文长度
  - 是否支持 reasoning 内容
  - 并发和单次输出限制
- 建立模型兼容验收集：
  - 守岸人人设遵循
  - 中文指令理解
  - 单次与连续工具调用
  - RAG 检索后回答
  - 长会话摘要续聊
  - 错误参数修正和工具失败恢复
- 保持 Embedding 服务独立：
  - 聊天模型与 Embedding 模型可使用不同服务
  - 更换聊天模型不强制重建知识库向量
  - 更换 Embedding 模型时沿用现有重嵌入流程
- 增加连接与故障策略：
  - 服务健康检查
  - HTTPS 与访问令牌
  - 请求限流和并发上限
  - 超时、重试与熔断
  - 私人模型不可用时切回已配置的备用模型
- 明确隐私边界：
  - 不上传完整数据库和工作区目录
  - 只发送本轮必要的记忆、RAG 片段和工具结果
  - 云端日志默认脱敏，不记录 API Key、完整文档和长期记忆
  - 服务端数据保留策略必须可配置和关闭
- 部署 PoC 时再选择推理引擎和模型，不在当前稳定化阶段锁定具体方案。

**进入条件**：

- S0-S4 的稳定性问题已基本收口。
- 至少三个高频私人助理场景已有固定验收样例。
- 已明确预算、并发需求、目标延迟和可接受的模型能力下限。

**验收**：

- 切换到私人模型只需要修改模型配置，不需要改 Agent 和工具代码。
- 私人模型能够稳定完成核心对话、RAG 和工具调用验收集。
- 云端服务不可用时，桌面端能明确报错或切换备用模型，不破坏会话状态。
- 本地数据库、原始知识库和工作区文件不会被整体上传。

## 6. 数据库路线建议

当前不建议立刻硬迁移数据库。推荐先按下面路径推进：

1. **保留 `sql.js`，完成审计和备份**
   这是最小风险路线，不打断当前项目。

2. **抽象 DB Repository**
   让业务逻辑少依赖 `sql.js` 具体 API，为迁移留出口。

3. **做 `better-sqlite3` PoC**
   验证 Windows + Electron + electron-builder 打包，不先碰业务主线。

4. **根据审计结果决定迁移**
   如果知识库和使用频率明显增长，迁移到原生 SQLite；否则继续增强 `sql.js` 的可靠性。

## 7. 私人模型路线建议

私人模型方向不需要现在立即租服务器或确定模型。当前只需要保证架构不把 Agent 绑定到百炼或其他单一服务：

1. **本地数据层保持独立**
   SQLite、记忆、知识库、工作区和工具执行继续由桌面端管理。

2. **模型接口保持标准化**
   优先以 OpenAI-compatible 接口作为自建服务接入面，模型差异由现有 adapter 和后续 capability profile 消化。

3. **聊天与 Embedding 分离**
   私人小模型可以只负责对话和工具决策，向量生成继续使用独立 Embedding 服务。

4. **先用验收集选模型**
   不只比较参数量和聊天观感，应以工具调用成功率、中文遵循、RAG 回答质量、延迟和运行成本判断是否可用。

5. **最后再决定是否迁移更多服务**
   云端模型不等于云端数据库。只有出现多设备共享需求时，才单独评估同步层或云端数据服务。

## 9. 完成标准

稳定化阶段完成后，应满足：

- `pnpm typecheck`、核心测试和构建可稳定通过。
- 数据库有备份、恢复和 migration 安全策略。
- 是否迁移原生 SQLite 有明确结论。
- Agent 运行失败、工具失败、语音失败都有可理解的降级。
- 工具/技能扩展有统一模板和验收规则。
- 知识库能长期扩充、重建、删除和评测。
- 守岸人人设与私人助理办事流程不互相拉扯。
- 模型服务具备可替换的兼容边界，后期切换私人小模型不需要重写 Agent 和工具系统。

*本计划是 M1-M7 之后的稳定化路线。新增大型能力前，优先完成 P0 和 P1 项。*
